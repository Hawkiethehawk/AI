## 0. 一句话理解

IAA（In-App Advertising）变现的本质是：把**用户会到达的广告机会**以尽量高的价格、尽量高的售卖成功率、尽量低的体验损伤卖出去。

```text
广告收入 = 展示次数 × eCPM / 1000
ARPDAU = 人均展示次数 × eCPM / 1000
人均展示次数 = 广告请求渗透率 × 人均请求 PV × 填充率 × 展示率
```

> 🧭 **贯穿全文的一句话**：IAA 运营的诊断主线永远是”人均展示次数 × eCPM”这棵收益树——先判断是量出了问题还是价出了问题，再一路拆到具体叶子。笼统地说”今天 eCPM 掉了”无法定位根因。

为什么这句很重要？因为几乎所有“收入下降”的抱怨，最后都会落到两类根因：

1. **卖出去的次数变少了**：用户没走到广告位、请求没发出、没填充、没 ready、没成功展示。
2. **同样的展示卖便宜了**：广告主出价下降、点击率下降、转化率下降、用户质量下降。

只要你把问题先分到这两类，后面的排查才会快。

## 1. 主脊柱：把收入拆成一棵可运营的收益树

内部资料里最有价值的不是某个平台参数，而是这套可复用的拆解方式：

```text
广告收入
├─ DAU
└─ ARPDAU
   ├─ 人均展示次数
   │  ├─ 广告请求渗透率
   │  ├─ 人均请求 PV
   │  ├─ 填充率
   │  └─ 展示率
   └─ eCPM
      ├─ 广告主出价
      ├─ 点击率（CTR）
      ├─ 转化率（CVR）
      ├─ 地区 / 渠道 / 用户质量
      └─ 广告样式与展示位置
```

穿山甲把收益进一步写成：

```text
收益 = 广告请求 × 填充率 × 展示率 × 点击率 × 转化率 × 广告主出价
```

这两个公式其实是一回事：一个偏 **业务看板视角**，一个偏 **广告转化漏斗视角** [[4]](https://www.csjplatform.com/growthcenter/6101274400195d0046c2731d)。

### 1.1 为什么这棵树比“盯大盘收入”更有用

因为它把“结果指标”改写成了“可操作叶子”：

- **收入掉了**，先看是 **DAU 掉** 还是 **ARPDAU 掉**。
- **ARPDAU 掉了**，再看是 **人均展示次数掉** 还是 **eCPM 掉**。
- **人均展示次数掉了**，继续看是 **渗透率、请求 PV、填充率、展示率** 哪个掉。
- **eCPM 掉了**，继续看是 **用户质量、CTR、CVR、广告主预算** 哪个在变。

> 💡 收益树最大的价值是把优化动作和指标节点一一对应。节点对应动作，日常复盘才不会变成空话。

### 1.2 每个叶子大概在管什么

| 叶子 | 它回答的问题 | 常见操作者 |
|---|---|---|
| 广告请求渗透率 | 有多少活跃用户真正走到了“会发广告请求”的路径 | 产品 / 客户端 |
| 人均请求 PV | 这些用户平均触发了多少次可售卖机会 | 产品 / 运营 |
| 填充率 | 发出的请求里，有多少拿到了广告 | 聚合 / 运营 |
| 展示率 | 拿到广告后，有多少真正展示成功 | 客户端 / 运营 |
| eCPM | 每千次展示平均卖了多少钱 | 运营 / 流量获取 / 聚合 |

### 1.3 一个简化示意，帮助你感受“量”和“价”谁更重要

下面数字仅为**示意**：

```text
方案 A：人均展示 4 次，eCPM 20
ARPDAU = 4 × 20 / 1000 = 0.08

方案 B：人均展示 2 次，eCPM 35
ARPDAU = 2 × 35 / 1000 = 0.07
```

看起来方案 B 单价更高，但最终人均收入更低。

> ⚠️ 这就是 IAA 最常见的误判：把”价格高”当成”收入高”。真正要最大化的是 ARPDAU / LTV，不应单独把 eCPM 顶到最高。

## 2. 第一大坑：只看 eCPM，不看售卖率、展示率和体验

如果只记一个新手误区，就记这一个。

内部 PPT 明确强调，广告收益取决于两个核心指标：

1. **广告售卖价格**（eCPM）
2. **广告售卖比率**（填充率 / 可卖成功率）

再往前一步，真正收入还要再乘上 **展示率**。所以实际逻辑是：

```text
只追高价，不管填充与展示 → 可能“理论很贵，实际上卖不出去”
只追高频，不管用户体验 → 可能“短期展示变多，长期留存变差”
正确目标 → 在体验可接受的前提下，让 ARPDAU / LTV 最大
```

### 2.1 为什么“高底价”经常把新人带偏

瀑布流里你很容易产生一种错觉：

- 既然高价层更值钱，
- 那就应该不断抬底价，
- 这样广告就会越来越贵。

但真实情况是：

- **底价提高**，高价广告源更难填满；
- **填充下降**，展示次数会变少；
- 如果减少的展示量大于提升的单价，**总收入反而下降**。

### 2.2 为什么“猛加广告位”也不一定赚更多

因为广告不是越多越好。频次过高会伤两件事：

1. **短期点击质量变差**：误点、厌烦、快速跳过，会伤 CTR/CVR。
2. **中长期留存变差**：用户更快流失，未来广告机会总量下降。

> 💡 IAA 的本质是平衡”当前展示价值”和”用户未来还能回来几次”。优秀变现方案一定要和留存一起看——这二者是同一个问题的两面。

## 3. 广告样式：按用户场景选，不按单价想象选

Google AdMob 将常见广告格式定义为 Banner、Interstitial、Rewarded、Native、App Open 等 [[1]](https://support.google.com/admob/answer/6128738?hl=en)。内部资料也把开屏、Banner、插屏、激励视频、原生广告作为新人必须理解的基础样式。

先记住一个原则：

> 🧭 **广告样式的选择标准是”哪个最匹配该场景下用户的注意力和容忍度”，单价高必须和场景匹配并行考虑。**

### 3.1 五种核心广告样式怎么理解

| 样式 | 官方定义 / 行业共识 | 典型工具产品场景 | 最关键的运营问题 |
|---|---|---|---|
| 开屏 / App Open | 用户打开或切回 App 时覆盖加载页展示 [[1]](https://support.google.com/admob/answer/6128738?hl=en) | 启动页、热启动回前台 | 不要拖慢进入；要有首屏兜底 |
| Banner | 顶部或底部常驻横幅 [[1]](https://support.google.com/admob/answer/6128738?hl=en) | 工具主页、结果页底部、列表页底部 | 不遮挡主操作；保持可见性 |
| 插屏 | 自然切换点展示的全屏广告 [[1]](https://support.google.com/admob/answer/6128738?hl=en) | 功能完成页、页面切换、退出前 | 只放自然断点，别打断正在操作 |
| 激励视频 | 用户主动观看以获得奖励 [[1]](https://support.google.com/admob/answer/6128738?hl=en) | 解锁权益、额外次数、去水印、导出前加成 | 奖励必须真有价值 |
| 原生广告 | 融入内容流和页面样式的可定制广告 [[1]](https://support.google.com/admob/answer/6128738?hl=en) | 信息流、工具推荐列表、结果页卡片 | 元素完整、标识清晰、别伪装成普通内容 |

### 3.2 从用户任务角度看“什么位置更合理”

可以把工具产品里的页面分成三类：

1. **进入前**：启动页、回前台页。
2. **任务中**：正在编辑、扫描、处理、导出、阅读。
3. **任务后**：结果页、完成页、确认页、奖励页。

对应广告友好度通常是：

```text
进入前：适合开屏，但要快
任务中：最危险，尽量少打断
任务后：最稳定，适合插屏 / 激励 / 原生推荐
```

> 💡 工具产品的高质量广告位，往往在”用户刚完成一个小目标、愿意停一秒”的位置。不一定要最显眼，但一定最自然。

### 3.3 为什么激励视频常被高估、也常被做坏

激励视频的优点非常明显：

- 用户是主动点的，抵触小；
- CTR / 完播 / 收益通常更好；
- 可以和权益体系绑定，兼顾体验与变现。

但它也最容易被做坏：

- 奖励不值钱，用户不会看；
- 入口太深，触发率低；
- 奖励描述不清，用户不信；
- 触发时机太奇怪，用户不理解为什么现在要看广告。

内部资料里反复提到，激励视频的核心不是“按钮放哪”，而是 **奖励本身是否真的解决用户当下需求**。

举几个更适合工具产品的激励设计思路：

- 看广告获得一次高清导出；
- 看广告解锁一次高级模板；
- 看广告增加一次识别 / 转写 / 生成功能次数；
- 看广告去除一次水印或延长一次使用时长。

比起“送 100 金币”这种游戏式抽象奖励，工具用户更能感知 **立即生效的功能权益**。

## 4. 广告位设计：本质是用户路径经营

很多团队把广告位设计理解成“这里插一个 ID，那里插一个 ID”。这是过于技术化的理解。

真正的广告位设计，应该从 **用户路径** 出发。

### 4.1 内部资料给出的基本方法

在《变现新人任务管理表》与常规问题整理里，广告方案设计的核心动作是：

1. 先理解产品功能和核心用户路径；
2. 画出主流程和自然断点；
3. 参考同类产品的广告场景；
4. 再决定什么位置适合什么样式；
5. 最后设计频次、顺序、兜底和异常回调。

### 4.2 一个实用框架：把用户路径分成 4 种广告机会

```text
A. 启动机会：用户刚进入应用，注意力集中，但容忍度低
B. 等待机会：用户在等结果、等跳转、等结束
C. 完成机会：用户刚做完一个动作，最适合插屏 / 推荐 / 激励
D. 欲望机会：用户想要更多权益，此时最适合激励视频
```

如果你拿这个框架去看工具 App，会更容易判断场景是否自然。

### 4.3 怎样判断一个广告位是不是“埋深了”

常见信号有：

- 页面层级太深，用户根本走不到；
- 只有很小比例用户能触发该功能；
- 即使到达页面，也停留极短；
- 位置在视觉角落，用户根本看不到；
- 触发前还有多个前置动作，路径太长。

穿山甲在展示率优化里明确说，一、二级页面的广告位往往比三级、四级页面更容易获得展示机会；如果要在更浅层做激励入口，可以通过首页宝箱、签到、权益入口等方式把广告机会前置 [[4]](https://www.csjplatform.com/growthcenter/6101274400195d0046c2731d)。

> ⚠️ 许多“填充低”“收入低”其实不是广告平台的问题，而是广告位根本没有足够用户到达。先看场景到达率，再怀疑平台。

## 5. 广告售卖方式：单一广告源、聚合、竞价分别解决什么问题

内部手册把广告售卖方式分为自售、联盟、集成化广告 / SDK 接入。对大多数工具 App 团队来说，现实工作重点不在自建销售，而在 **多广告源管理**。

### 5.1 单一广告源的优缺点

优点：

- 接入简单；
- 数据口径相对单纯；
- 问题定位较直接。

缺点：

- 对单一平台预算依赖大；
- 某个国家 / 机型 / 时段一旦没量，填充容易波动；
- 议价与兜底空间小。

### 5.2 聚合（Mediation）到底在解决什么

AdMob 官方把 mediation 定义为：让应用从多个来源投放广告，包括 AdMob Network、第三方广告网络和 AdMob campaigns；但前提是每个网络都正确完成接入和配置 [[2]](https://support.google.com/admob/answer/9469204?hl=en)。

MAX 则把自身定位成可同时接入 bidding 与传统网络的中介层，并强调：

- 尽早初始化 SDK，给缓存留时间；
- 通过调试器和测试工具验证接入；
- 为插屏 / 激励建立加载失败重试与关闭后立刻加载下一条的机制 [[3]](https://support.applovin.com/en/max/getting-started)。

翻译成运营语言，聚合主要解决 3 件事：

1. **更多需求方竞争同一个展示机会**；
2. **单一平台预算波动时的填充兜底**；
3. **让排序、分层、分组成为可调策略**。

### 5.3 聚合引入了什么新的复杂度

你拿到的不是“白送的更高收益”，而是“更高上限 + 更高管理复杂度”：

- 需要管多个 SDK；
- 需要管多套账号、广告位 ID、报表 API；
- 需要理解 waterfall / bidding / hybrid；
- 需要区分 SDK 统计、API 数据、预估收益、结算收益；
- 需要处理展示 GAP、时区差、缓存与回调问题。

> 💡 聚合的价值是”接得进、调得动、看得清”。看不清数据口径的聚合，只会让团队更混乱。

## 6. 广告链路：所有诊断都应该先回到漏斗

内部 PPT 给出的基础链路是：

```text
发起请求 → 返回广告 → 广告展示 → 点击 / 转化
```

TopOn 把它扩展成更适合日常定位问题的运营漏斗 [[5]](https://help.toponad.net/cn/docs/qlHqYM)：

```text
应用启动 / SDK 初始化
→ 获取策略
→ 请求广告
→ 填充广告
→ 到达广告场景
→ 广告 ready
→ 触发展示
→ 展示成功
→ 点击
```

### 6.1 为什么漏斗是运营最重要的报表之一

因为收益树告诉你“是哪棵枝杈出了问题”，漏斗报表告诉你“问题具体断在链路哪一段”。

比如：

- **请求少**：更像产品路径 / 触发逻辑问题；
- **填充少**：更像平台预算 / 分层 / 用户质量问题；
- **ready 低**：更像预加载和缓存时机问题；
- **展示低**：更像展示代码、素材可见性、广告有效性问题；
- **点击低**：更像样式、位置、可点击元素问题。

### 6.2 TopOn 漏斗里几个特别值得记住的指标

根据 TopOn 文档 [[5]](https://help.toponad.net/cn/docs/qlHqYM)：

- **流量填充率 = 流量填充 / 流量请求**
- **广告场景到达率 = 到达广告场景设备数 / 应用启动设备数**
- **广告 Ready 率 = 用户到达广告场景时广告已经 ready 的占比**
- **广告触发率 = 触发展示次数 / 到达广告场景次数**
- **展示成功率 = 展示次数 / 触发展示次数**

这几个指标非常适合把“量出了问题”继续拆深。

### 6.3 一个实用诊断地图

| 漏斗掉点 | 更可能是什么问题 | 第一动作 |
|---|---|---|
| 获取策略低 | SDK 初始化 / 拉策略逻辑不稳 | 查初始化与配置拉取日志 |
| 请求低 | 用户没走到场景、代码没发请求、频控过严 | 回看触发路径和触发条件 |
| 填充低 | 底价高、广告源少、平台预算波动、用户质量差 | 看平台 / 国家 / 广告源分布 |
| Ready 低 | 请求太晚、缓存失效、没预加载 | 调整预加载时机与缓存机制 |
| 触发低 | 激励不够、入口太深、触发逻辑弱 | 改入口与触发文案 |
| 展示低 | show 失败、viewability 不够、素材被遮挡 | 查展示回调与 UI 可见性 |
| 点击低 | 样式弱、元素不可点、广告尺寸小 | 优化创意承载区域 |

> 💡 诊断的顺序最好是“先上游、后下游”。因为下游差，经常只是上游问题传导出来的结果。

## 7. 并行、瀑布流、竞价：三种核心调度逻辑到底差在哪

这是 IAA 学习中最容易“词懂了、实战没懂”的一章。

### 7.1 并行请求：优先解决“有没有广告可卖”

内部手册把并行描述为：同时请求多家平台，按一定比例展示广告，优点是能保证填充率、请求链路较短、响应快。

你可以把它理解成：

```text
多个广告源一起抢时间
谁先有可展示资源，系统更容易拿到可卖广告
```

优点：

- 填充相对更稳；
- 响应速度快；
- 对新产品、冷启动位置更友好。

代价：

- 可能造成“请求很多、实际展示较少”；
- 对广告使用率不友好；
- 数据反馈复杂；
- 如果并行过多，可能浪费带宽并伤平台对资源利用率的判断。

### 7.2 瀑布流（Waterfall）：优先解决“能不能卖得更贵”

内部资料定义得很清楚：

- 通过设置 eCPM 底价把广告源分层；
- 从高价层开始请求；
- 高层无填充，再往下落。

```text
高价层 → 中价层 → 低价层 → 兜底层
```

为什么它常见？因为它满足运营最核心的控制欲：

- 你可以决定谁先请求；
- 你可以按国家 / 机型 / 广告位单独调价；
- 你可以很明确地做高价流量优先售卖。

但它的天然代价也很明显：

- 请求链路更长；
- 分层太多时加载更慢；
- 底价调高就更容易掉填充；
- 维护工作量大。

内部 PPT 提到“比较合理的分层在 10–20 层区间”这一说法，这属于团队 / 场景经验口径，不应机械当成通用行业硬阈值；真正应以自己的网络条件、国家结构、广告位类型和填充表现实测为准。

### 7.3 竞价（Bidding）：优先解决“谁真的愿意为这次展示出最高价”

内部资料把 Header Bidding 解释为：让多个平台 SDK 同时公平竞价，避免传统瀑布流里低顺位平台的优质 offer 被错过。

MAX 也强调它支持 bidding 与传统连接并存 [[3]](https://support.applovin.com/en/max/getting-started)。

用更直白的话说，竞价是在替你做一件瀑布流做不好的事：

> 同一时刻、同一个曝光机会，让多个需求方更实时地出价，竞价替代了你手动预测”谁大概更值钱”的瀑布流分层。

## 7.4 实战里最常见的是 Hybrid

现实里很多成熟团队不会只用纯瀑布或纯竞价，而是：

```text
Bidding 池负责更实时地抬价
Waterfall 负责兜底和补填充
```

这就是常说的 Hybrid。

> ⚠️ 对新团队来说，最容易犯的错是”基础链路还没稳，就急着上复杂调度”。先把请求、ready、展示、口径、API 拉通，再谈更高级的排序优化。

## 8. 预加载、缓存和兜底：为什么很多收入问题其实是工程问题

很多运营同学会本能地把收入问题归到“平台没量”“底价没配好”。但内部资料与 MAX / TopOn 文档都在强调：**很多问题其实卡在加载与展示工程上**。

### 8.1 预加载到底解决什么

预加载解决的是：当用户走到该场景时，广告能已经 ready，无需现加载现等。

尤其是视频类广告文件大、加载慢，如果不提前准备，用户到达场景时就可能没广告可看。

穿山甲文档明确提醒：

- 预加载有助于提高展示率；
- 但预加载不是越早越好；
- 如果预加载成功却长期不展示，反而会影响系统对该流量价值的判断 [[4]](https://www.csjplatform.com/growthcenter/6101274400195d0046c2731d)。

这其实是在提醒你做 **时机平衡**：

- 太晚：来不及 ready；
- 太早：缓存过期 / 请求浪费 / 使用率下降。

### 8.2 内部预加载逻辑里最值得学的是思路，不是具体数值

内部自建聚合逻辑包含：

- 启动后初始化 SDK；
- 根据策略预加载；
- 成功则进入缓存池；
- 失败则继续下一个广告源；
- 全部失败则下一轮再拉；
- 兜底层可预先缓存最低层广告；
- 展示后立即补下一条。

内部还给出过一些实现示例，如 `8s` 超时、`30s` 下一轮触发、每策略 `2` 条缓存、缓存半小时、单广告源连续失败 `6` 次后跳过。这些都属于**当前团队实现口径**，学习重点在于它背后的方法：

1. **有缓存池，而不是每次裸请求**；
2. **失败要有顺延和重试策略**；
3. **展示后要立刻补货**；
4. **要有兜底，不让场景空转**。

### 8.3 MAX 官方为什么反复强调“尽早初始化、失败重试、展示后立刻加载下一条”

MAX 的入门最佳实践里，明确建议 [[3]](https://support.applovin.com/en/max/getting-started)：

- App 一启动就初始化 SDK；
- 插屏 / 激励在初始化后就开始加载；
- 加载失败或展示失败时做指数退避重试；
- 用户关闭插屏 / 激励后，立刻加载下一条；
- Banner 尽量持续保持在屏幕上，避免因 viewability 失效造成无效展示。

> 💡 这些建议的本质都是同一个目标：不要让“本来能卖掉的曝光机会”因为你准备得不够早而错过。

## 9. 数据口径：结算数据、SDK 数据、预估数据千万别混着看

这是 IAA 第二个高频坑，而且非常致命。

TopOn 在数据 GAP 文档里讲得非常明确：数据分两大类 [[6]](https://help.toponad.net/cn/docs/Z4zsF6)：

1. **三方 API 数据**：来源于广告平台 API，需要授权拉取，属于更接近结算的数据。
2. **TopOn 统计数据**：来源于 SDK 埋点，主要用于过程监控与排障，不等于最终结算。

### 9.1 最简单的记法

```text
对账 / 收益确认 → 看三方平台后台或 API 数据
漏斗 / 排障 / 实时过程 → 看 SDK 统计数据
```

### 9.2 为什么两者一定会有差异

因为它们统计的不是同一件事：

- SDK 统计的是“我收到了展示成功回调”；
- API 数据统计的是“平台认定这次曝光最终有效并计入报表”；
- 两者之间还会受到时延、时区、网络丢包、无效展示过滤等影响 [[5]](https://help.toponad.net/cn/docs/qlHqYM) [[6]](https://help.toponad.net/cn/docs/Z4zsF6)。

### 9.3 几个必须区分的名词

根据 TopOn 文档 [[6]](https://help.toponad.net/cn/docs/Z4zsF6)：

- **展示**：TopOn 收到平台 SDK 展示成功回调的次数。
- **展示 API**：TopOn 通过平台报表 API 拉到的曝光次数。
- **eCPM**：实际收益 ÷ TopOn 统计展示。
- **eCPM API**：实际收益 ÷ 展示 API。
- **预估 eCPM / 预估收益**：基于排序价、竞价实时价或历史价格推算的过程值。

### 9.4 这会怎么影响你的日常判断

| 你在做什么 | 应优先看什么 | 不该混用什么 |
|---|---|---|
| 判断今天广告位有没有跑起来 | SDK 漏斗数据 | 不要拿实时 SDK 去跟昨日结算硬比 |
| 算真实收入 / 对账 | 平台后台 / API 数据 | 不要拿预估收益当结算收益 |
| 查某位置为什么 ready 低 | SDK 数据与日志 | 不必先看收益 API |
| 查为什么展示差很多 | 展示 vs 展示 API 的 GAP | 不要只看总收入波动 |

> ⚠️ 只要你把“排障口径”和“结算口径”混在一起，团队里就会不断出现“明明展示很多为什么收入不对”“明明报表说没问题为什么线上没广告”的无效争论。

## 10. 如何读懂 eCPM：它到底由什么决定，哪些能控、哪些不能控

穿山甲把 CPM 拆成：

```text
CPM = 广告主出价 × 点击率 × 转化率 × 1000
```

这是非常好的教学公式 [[4]](https://www.csjplatform.com/growthcenter/6101274400195d0046c2731d)。

### 10.1 其中哪些是你能直接动的

**相对更可控：**

- 广告位置和时机；
- 广告样式与尺寸；
- 可点击元素设计；
- 用户路径是否顺；
- 预加载与展示成功率；
- 渠道 / 国家 / 用户分层后的运营策略。

**相对不可控：**

- 广告主大盘预算；
- 节假日 / 活动节点的整体出价波动；
- 平台侧对用户价值和转化概率的判断模型。

### 10.2 为什么 eCPM 下跌常常不是“变现团队自己能修”的

内部常规问题整理里写得很直白：

- 平台预算减少，会同时打击填充率和 eCPM；
- 用户质量下降，平台会不愿给更多或更高价的广告资源；
- 有时候真正该调的是买量端，而不是变现端。

### 10.3 CTR / CVR 提升为什么不能靠“误点”来赌

内部资料提到，误点可能短期抬 CTR，但如果后向转化跟不上，eCPM 未必能真正抬起来，反而会伤体验与留存。

穿山甲在点击率优化里给出的正确方向是 [[4]](https://www.csjplatform.com/growthcenter/6101274400195d0046c2731d)：

- 广告元素完整展示；
- 在不伤体验前提下适当增大广告尺寸；
- 扩大合理可点击区域，而不是只留一个很小按钮；
- 保证转化路径通畅，缩短点击后的跳转路径。

> 💡 真正高质量的 CTR，是“用户愿意点”，不是“用户不小心点”。前者能带来更高后向转化，后者往往只会带来更高反感和更差长期价值。

## 11. 为什么收入波动时，要先区分“平台预算问题”还是“用户质量问题”

这是内部资料里特别实战的一点。

当你发现填充率和 eCPM 同时下滑，通常先考虑两个大方向：

### 11.1 广告平台预算波动

典型特征：

- 多个广告位、多个产品同时波动；
- 节假日、周末、大促节点前后明显变化；
- 某个平台在特定国家明显下滑；
- 其他产品 / 行业也在反馈类似情况。

动作：

- 扩充更多广告平台做资源互补；
- 调整 waterfall 分层与兜底；
- 与平台 BM / 支持同学沟通；
- 分国家、分平台、分广告位看波动范围。

### 11.2 用户质量下降

典型特征：

- 同一个平台，不同渠道用户 eCPM 差异很大；
- 新增来源变了之后，收入同步变化；
- CTR / CVR / 填充都变差；
- 开屏等几乎不可操作的位置，eCPM 也同步走弱。

动作：

- 回到买量端查看渠道、版位、机型、地区、素材变化；
- 对比历史高质量用户包的行为特征；
- 必要时新建广告位 ID 做重新测试；
- 不要只在变现端做局部调价，忽视了流量质量根因。

> 💡 一个很实用的经验：**开屏 eCPM 的可操作空间很小，所以它反而是用户质量的好信号。** 如果连开屏都明显走弱，先别急着怪广告位设计。

## 12. 漏斗诊断：按“哪一格掉了”去开动作单

这一章是整篇文档最偏 SOP 的部分。

### 12.1 如果请求渗透率低，先查什么

重点怀疑：

- SDK 初始化成功率；
- 广告配置获取成功率；
- 广告请求代码是否真的执行；
- 新版本是否改了路径 / 埋点；
- 某些国家 / 渠道是否触发条件不同。

适合动作：

- 查初始化日志、版本日志；
- 对比新旧版本漏斗；
- 对比不同渠道、不同页面的请求率；
- 回到产品流程图看“用户有没有机会走到这里”。

### 12.2 如果填充率低，先查什么

TopOn 在漏斗文档里给的第一个建议就是：当流量填充明显少于流量请求时，可以考虑在 waterfall 里增加无底价广告源做兜底 [[5]](https://help.toponad.net/cn/docs/qlHqYM)。

除此之外再看：

- 底价是不是太激进；
- 某个广告源是不是近期预算不足；
- 是否广告平台过少；
- 用户质量是否变差；
- 某国家 / 某广告位是不是结构性差异。

### 12.3 如果 Ready 率低，先查什么

TopOn 明确提示：Ready 率低时，应该结合填充率一起看 [[5]](https://help.toponad.net/cn/docs/qlHqYM)：

- **填充高、Ready 低**：多半是请求太晚，用户到场景时还没准备好。
- **填充低、Ready 也低**：更像 waterfall 配置本身有问题。

对应动作：

- 调整预加载时机；
- 增加自动加载或缓存逻辑；
- 复查缓存有效期；
- 检查展示前 isReady 查询是否过于频繁或时机不合理。

### 12.4 如果展示成功率低，先查什么

TopOn 文档和 MAX 最佳实践都在提示同一件事：**拿到广告不等于成功展示。**

常见原因：

- show 调用时机不对；
- 广告过期；
- UI 遮挡；
- Banner / 原生不可见面积不够；
- 开屏展示面积不达平台有效展示要求；
- 集成有问题，回调和场景 ID 传错。

TopOn 给出的常见有效展示优化包括 [[6]](https://help.toponad.net/cn/docs/Z4zsF6)：

- 不要遮挡、扭曲、模糊广告内容；
- 原生 / Banner 的展示时长与面积要满足平台要求；
- 开屏广告展示面积要足够，别让自家 logo 挤占太多屏幕。

### 12.5 如果点击率低，先查什么

优先怀疑：

- 广告尺寸太小；
- 元素不完整；
- 点击区域做得太保守；
- 样式和页面环境不匹配；
- 广告出现时机不自然。

穿山甲特别指出，原生广告不应只让“下载按钮”可点，其它元素也应是合理可点击区，因为相当一部分点击来自卡片其他元素 [[4]](https://www.csjplatform.com/growthcenter/6101274400195d0046c2731d)。

## 13. 展示 GAP / 收益 GAP：什么时候是正常差异，什么时候该报警

TopOn 的 GAP 排查文档是很好的“口径课” [[6]](https://help.toponad.net/cn/docs/Z4zsF6)。

### 13.1 先记住两个最常见的 GAP

1. **展示 GAP**
   - 公式：`(展示 - 展示API) / 展示API`
   - 含义：SDK 统计的展示与平台 API 认定展示之间的差异。

2. **收益 GAP**
   - 含义：TopOn/聚合侧的预估收益或 API 收益，与平台实际收益之间的差异。

### 13.2 什么情况下先别急着慌

TopOn 明确提醒：

- API 数据拉取有时延；
- 不同时区会天然产生偏差；
- 最新数据并不总是稳定；
- 预估收益与真实收益本来就不可能完全重合 [[6]](https://help.toponad.net/cn/docs/Z4zsF6)。

所以在看到 Gap 时，先做三件事：

1. 确认比较的是同一天、同时区；
2. 确认 API 授权已经开通；
3. 确认数据是否已经过了平台 / 聚合的更新时间。

### 13.3 什么情况下该重点排查代码或无效展示

如果展示 API 明显小于 SDK 展示，TopOn 建议继续查：

- 是否有老版本没有通过聚合 SDK 请求广告；
- 是否存在广告位 ID 复用；
- 是否某个广告源被平台判定为无效展示；
- 是否 Banner / 原生被遮挡、可视面积不足；
- 是否展示时长太短。

> ⚠️ 收益差很多时，别一上来就怪平台“偷量”。先从时区、API 授权、ID 复用、展示有效性和老版本分流这些最常见原因查起。

## 14. A/B 测试：小流量、强护栏、看全链路

内部 PPT 对 A/B test 的定义很准确：通过比较多种变现策略，用真实数据选最优方案，而且一般按用户属性分组，不会大尺度破坏用户体验。

### 14.1 IAA 里最值得测的东西

- 新旧广告位位置；
- Waterfall 排序与底价；
- 激励视频入口文案 / 奖励强度；
- 插屏频率、间隔、触发时机；
- 预加载时机与缓存条数；
- 兜底广告源是否开启；
- 新广告样式（如原生改版、Banner 尺寸变化）。

### 14.2 测试时不能只看一个指标

建议至少拆成三层：

```text
主指标：ARPDAU / 人均广告收入 / LTV
过程指标：渗透率、请求率、填充率、展示率、eCPM、CTR
护栏指标：D1 / D7 留存、时长、启动次数、投诉、卸载、付费转化
```

### 14.3 为什么“eCPM 提升了”不能直接宣布胜利

因为有几种常见假象：

- 频率降了，低价值展示少了，eCPM 看起来高了，但总收入变低；
- 用户被打断更多，短期收入升了，但 D7 留存明显变差；
- 某个国家提价有效，但整体样本结构变了，结论不稳定。

> 💡 广告实验必须看“价格 × 量 × 留存”。少看任何一条，都会把团队带偏。

## 15. 新产品 / 新广告位上线 SOP：把“设计—配置—验收—复盘”串起来

根据《变现新人任务管理表》，可以把 IAA 上线流程整理成一条更适合执行的 SOP：

```text
产品提出需求
→ 研究市场 / 同类产品 / 商业化模式
→ 补齐产品基础信息、参数、素材包
→ 对接产品主路径与商业化设计
→ 输出广告埋点方案
→ 申请投放参数与广告参数
→ 后台创建广告源和广告位配置
→ 测试包验收（样式 / 触发 / 回调 / 数据）
→ 切正式广告 ID / 正式配置
→ 上线监控与数据复盘
```

### 15.1 广告埋点方案至少要写清什么

- 广告位名称与 ID；
- 所在页面与触发条件；
- 广告样式；
- 展示频次 / 间隔 / 上限；
- 预加载时机；
- 兜底逻辑；
- 回调事件；
- 是否区分国家 / 渠道 / 版本策略。

### 15.2 验收时不要只看“有没有出来”

MAX 和 AdMob 的官方排障文档都强调：新 App / 新 ad unit 有时需要激活时间，另外要用测试模式、调试器、错误码和检查器来验证接入 [[2]](https://support.google.com/admob/answer/9469204?hl=en) [[3]](https://support.applovin.com/en/max/getting-started)。

所以验收要覆盖：

1. **显示层**：样式对不对、是否遮挡、是否符合设计；
2. **功能层**：请求、ready、show、关闭、奖励、失败重试是否正常；
3. **数据层**：日志、回调、漏斗埋点、广告平台后台是否连通；
4. **策略层**：频控、生效国家、版本、流量组、广告源优先级是否符合预期。

## 16. 新人学习路径：从“会看报表”到“能独立带一条产品线”

内部任务管理表给出的 3 个月路径很值得保留，因为它本质上对应了 IAA 能力的三层递进。

### 第 1 阶段：理解框架（学习期）

目标不是立刻调高收入，而是把基本地图建立起来：

- 了解产品商业模式与核心产品；
- 认识主要广告平台与聚合后台；
- 理解广告样式、展示链路、基础配置；
- 会看核心指标；
- 能用历史数据做基础漏斗分析。

### 第 2 阶段：会做诊断（实践期）

开始能独立回答一些关键问题：

- 为什么这个广告位请求低？
- 为什么这个位置 ready 低？
- 为什么某个渠道带来的用户 eCPM 差？
- 这个产品该加什么样式、放在哪个断点更合理？

### 第 3 阶段：会做策略（产出期）

真正成熟的标志，不是“会改一个底价”，而是：

- 能负责一条产品线的商业化设计；
- 能串产品、投放、客户端、数据一起工作；
- 能提出策略假设并验证；
- 能输出复盘与案例。

> 💡 IAA 运营成熟度的提升路径通常是：**记指标 → 看漏斗 → 找根因 → 提策略 → 做验证 → 形成 SOP。**

## 17. 常见误区速扫

1. **只看 eCPM，不看展示量。** 高价但没量，收入照样差。
2. **只看填充率，不看单价。** 全填低价流量，也可能浪费高价值展示机会。
3. **把广告位设计理解成“插几个点”。** 没有用户路径分析，广告位很容易埋深。
4. **预加载越早越好。** 错。太早会导致缓存浪费、展示率下降、甚至影响平台判断。
5. **接的广告源越多越好。** 数据看不清、调不动的广告源只会增加噪音。
6. **SDK 统计就是结算收入。** 错。SDK 看过程，API / 平台后台看结算。
7. **CTR 可以靠误点做高。** 短期也许有效，长期很可能伤 CVR、留存和平台判断。
8. **看到 GAP 就认为平台有问题。** 先排时区、API 授权、ID 复用、有效展示与老版本分流。
9. **A/B 只看收入。** 不看留存和投诉，可能是在透支产品。
10. **新版本上线不分版本看漏斗。** 很多变现问题其实是新版本逻辑变了。
11. **把竞价当万能药。** 基础链路没稳时，上复杂调度只会放大问题。
12. **变现和买量割裂。** 用户质量问题，经常会先体现在 eCPM 和填充上。

## 附：一页速查表

```text
核心公式
广告收入 = 展示次数 × eCPM / 1000
ARPDAU = 人均展示次数 × eCPM / 1000
人均展示次数 = 广告请求渗透率 × 人均请求 PV × 填充率 × 展示率
CPM = 广告主出价 × 点击率 × 转化率 × 1000

收益树
收入 = DAU × ARPDAU
ARPDAU = 人均展示次数 × eCPM / 1000
人均展示次数 = 渗透率 × 人均请求PV × 填充率 × 展示率

广告链路
初始化 → 获取策略 → 请求 → 填充 → 到达场景 → Ready → 触发展示 → 展示成功 → 点击/转化

三种调度逻辑
并行：优先保证填充与响应速度
瀑布流：优先提高售卖价格，但维护成本高
Hybrid：竞价抬价 + 瀑布兜底，是成熟常见形态

四类常见问题
请求低：场景埋深 / 代码未触发 / 频控过严
填充低：底价高 / 广告源少 / 平台预算不足 / 用户质量差
Ready低：预加载太晚 / 缓存失效 / 请求时机不对
展示低：展示失败 / UI遮挡 / 无效展示 / 广告过期

数据口径
排障看 SDK / 漏斗
对账看 API / 平台后台
不要把预估收益当结算收益

上线 SOP
需求 → 场景设计 → 参数准备 → 广告配置 → 测试包验收 → 正式切量 → 上线监控 → 日常复盘
```

## 0. 一句话理解

混变工具的数据埋点，目标是让用户生命周期、广告收入、订阅收入、归因成本能够在同一套 cohort 里被解释。

```text
总收入 = IAA 收入 + IAP 收入
IAA 收入 = 展示次数 × eCPM / 1000
IAP 收入 = 付费墙触达 × 购买/试用转化 × 续订留存 × 净单价
ROI = cohort LTV / cohort CAC
```

> 🧭 **贯穿全文的一句话**：混变数据系统的目标是，每次收入波动都能被拆到用户、场景、广告、付费、渠道、版本中的某个具体原因。

---

## 1. 主脊柱：用户生命周期 × 变现路径

先画路径，再定事件。一个混变工具产品至少有五层：

```text
获客 / 归因
→ 首次打开 / 同意 / onboarding
→ 核心任务完成
→ 变现触点
   ├─ IAA：广告场景 → 请求 → 填充 → 展示 → 收入
   └─ IAP：付费墙 → 点击 → 购买 → 权益 → 续订
→ 留存 / 复购 / 回收
```

Firebase 文档把事件定义为用于理解 App 中发生了什么，包括用户操作、系统事件或错误，并支持推荐事件和自定义事件 [[1]](https://firebase.google.com/docs/analytics/events)。Mixpanel 的 Tracking Plan 方法也强调先定义 KPI，再映射用户流程，再翻译成事件与属性 [[4]](https://docs.mixpanel.com/docs/tracking-best-practices/tracking-plan)。

> 💡 从业务问题反推埋点，而不是从页面按钮反推埋点。按钮会变，用户路径和收入问题相对稳定。

---

## 2. 第一大坑：客户端行为数不是收入真相

混变产品有四类数据口径：

| 口径 | 来源 | 用途 | 风险 |
|---|---|---|---|
| 客户端行为事件 | Firebase、Mixpanel、Amplitude、自建埋点 | 漏斗、路径、实时排障 | 丢包、重复、离线补发 |
| 广告收入事件 | AdMob ILRD、聚合 SDK、广告网络 | 用户级广告 LTV、近实时分析 | 可能是估算，不等于最终结算 |
| 订阅 / 支付状态 | App Store、Google Play、RevenueCat、Adapty、自建服务端 | 权益、续费、退款、状态机 | 回调延迟，状态复杂 |
| 归因 / 成本 | AppsFlyer、Adjust、广告平台 | ROI、ROAS、渠道优化 | 归因窗口与隐私限制 |

> ⚠️ 第一大坑：把 `ad_impression`、`purchase_success`、MMP 收入回传当成同一种“收入”。正确做法是：行为漏斗用事件，收入分析用可解释口径，财务对账用结算口径。

## 3. 事件设计原则：事件少而稳，属性准而全

Mixpanel 把事件作为数据模型核心，事件属性用于描述行为上下文，以便过滤、拆分和聚合 [[5]](https://docs.mixpanel.com/docs/data-structure/events-and-properties)。商业化埋点最重要的是稳定性和可拆分性。

### 3.1 六类核心事件

```text
生命周期：app_open / first_open / session_start / consent_update
核心任务：task_start / task_complete / result_view / export_success
广告链路：ad_scene_enter / ad_request / ad_load_success / ad_show / ad_impression / ad_click / ad_reward
付费链路：paywall_trigger / paywall_show / package_click / purchase_start / purchase_success / entitlement_granted
订阅状态：trial_start / renewal / cancel / billing_retry / grace_period / refund / expire
实验配置：experiment_exposed / remote_config_applied / pricing_variant
```

GA4 推荐事件覆盖 `ad_impression`、`purchase`、`refund`、`login`、`sign_up`、`tutorial_begin`、`tutorial_complete` 等常见事件 [[2]](https://support.google.com/analytics/answer/9267735)。能用推荐事件时优先用推荐事件，业务独有行为再自定义。

### 3.2 每个事件必须带的公共属性

```text
user_id / anonymous_id / install_id
app_version / build_number / platform / os_version
country / language / timezone
media_source / campaign / adset / creative
experiment_id / variant_id
event_time / client_time / server_time
```

### 3.3 收入事件必须带的属性

```text
monetization_type: iaa / iap / subscription
value
currency
is_estimated
revenue_source
transaction_id / impression_id（按权限和隐私要求处理）
```

## 4. IAA 埋点：只埋展示不够，要埋广告链路

广告链路最小闭环：

```text
ad_scene_enter
→ ad_request
→ ad_load_success / ad_load_fail
→ ad_ready
→ ad_show_attempt
→ ad_impression
→ ad_click
→ ad_reward_granted（如激励视频）
```

关键参数：

| 参数 | 用途 |
|---|---|
| ad_placement_id | 区分广告位 |
| ad_format | banner / interstitial / rewarded / native / app_open |
| ad_network | 实际展示广告网络 |
| mediation_platform | 聚合平台 |
| scene | 任务完成页、导出页、首页等 |
| load_latency_ms | 定位加载慢 |
| error_code | 定位失败原因 |
| value / currency | 展示级收入分析 |
| is_first_ad_in_session | 判断首广告价值 |

没有 `ad_scene_enter`，你只能知道广告展示下降，却不知道是用户没到场景、没请求、没填充，还是没展示成功。

---

## 5. IAP 埋点：只埋购买成功不够，要埋意图和状态

付费漏斗最小闭环：

```text
paywall_trigger
→ paywall_show
→ package_view
→ package_click
→ purchase_start
→ purchase_success / purchase_fail
→ receipt_validate_success
→ entitlement_granted
```

订阅状态机事件：

```text
trial_start
→ subscription_active
→ renewal_success
→ renewal_failed
→ grace_period
→ recovered / expired
→ cancel / refund / revoke
```

关键参数：

| 参数 | 用途 |
|---|---|
| paywall_id | 分析付费墙版本 |
| trigger_scene | 触发来源 |
| product_id / offer_id | 商品与优惠 |
| billing_period | 周 / 月 / 年 |
| price / currency | 价格分析 |
| failure_reason | 购买失败排查 |
| entitlement_id | 权益发放 |
| transaction_id | 交易去重与校验 |

## 6. 漏斗分析：把“掉了”变成“掉在哪”

GA4 漏斗探索可呈现用户完成任务经历的步骤，并定位每一步的成功或流失 [[3]](https://support.google.com/analytics/answer/9327974)。Amplitude Funnel Analysis 也用于理解用户如何沿定义路径移动并识别流失区域 [[6]](https://amplitude.com/docs/analytics/charts/funnel-analysis/funnel-analysis-build)。混变产品至少要建三条漏斗。

### 6.1 核心任务漏斗

```text
app_open → task_start → task_complete → result_view → export_success
```

它解释 DAU 和留存质量，也解释广告与付费触点的上游流量。

### 6.2 广告漏斗

```text
ad_scene_enter → ad_request → ad_load_success → ad_show → ad_impression → ad_revenue
```

它解释 IAA 收入波动。

### 6.3 付费漏斗

```text
paywall_show → package_click → purchase_start → purchase_success → entitlement_granted → renewal
```

它解释 IAP 收入波动。

> 💡 三条漏斗不能孤立看。付费墙曝光下降，可能不是付费墙问题，而是核心任务完成率下降，导致用户根本没到触发场景。

## 7. 归因与 ROI：渠道数据要接上收入数据

AppsFlyer SDK 支持记录应用内事件，用于归因后行为分析 [[7]](https://dev.appsflyer.com/hc/docs/in-app-events-ios)。Adjust SDK 也支持发送事件信息，用于移动归因与后续行为衡量 [[8]](https://dev.adjust.com/en/sdk/ios/features/events)。运营上要把渠道、成本、广告收入、IAP 收入放进同一 cohort。

最小 ROI 数据模型：

```text
install_id / user_id
+ media_source / campaign / adset / creative
+ country / platform / app_version
+ cost
+ ad_revenue
+ purchase_revenue
+ renewal_revenue
- refund
= cohort LTV / CAC / ROAS
```

如果只把购买事件回传给 MMP，而不回传广告收入，IAA 产品会低估渠道价值；如果只回传广告收入，不回传订阅状态，混变产品会低估高付费渠道。

---

## 8. 隐私与同意：数据可用性的边界

Apple 要求开发者说明数据收集实践，并在追踪用户前请求许可 [[9]](https://developer.apple.com/app-store/user-privacy-and-data-use/)。Google 的 Apps consent mode 说明了在 App 中如何根据用户同意状态控制 `ad_storage`、`analytics_storage`、`ad_user_data`、`ad_personalization` 等 [[10]](https://developers.google.com/tag-platform/security/guides/app-consent)。

埋点方案必须记录：

```text
consent_status
att_status（iOS）
analytics_storage
ad_storage
ad_personalization
privacy_region
```

> ⚠️ 不要把未同意用户和已同意用户混成同一口径后直接做投放结论。隐私状态会影响归因、个性化广告、分析可用性和收入表现。

## 9. 分析 SOP：收入波动怎么查

### 9.1 总收入下降

```text
总收入下降
├─ DAU / 新增下降？
├─ IAA 下降？
│  ├─ 广告场景到达下降
│  ├─ 请求 / 填充 / 展示下降
│  └─ eCPM 下降
└─ IAP 下降？
   ├─ paywall_show 下降
   ├─ purchase_start / success 下降
   ├─ renewal 下降
   └─ refund / cancel 上升
```

### 9.2 广告收入下降

优先按广告位、国家、平台、版本拆：场景到达、请求、填充、展示、eCPM 哪个动了。

### 9.3 付费收入下降

优先按付费墙版本、商品包、渠道、国家拆：曝光、点击、购买、校验、权益、续费、退款哪个动了。

### 9.4 ROI 下降

优先拆成本和 LTV：是 CAC 上升，还是广告 / 订阅回收下降；再看归因窗口、数据延迟和渠道结构。

## 10. 数据治理：没有字典，埋点会慢慢失效

一套可运营的埋点系统必须有：

- 事件字典：事件名、定义、触发时机、负责人。
- 参数字典：字段类型、枚举值、是否必填。
- 版本记录：什么时候新增、废弃、改名。
- 去重规则：交易、广告展示、服务端回调。
- 口径说明：估算、结算、归因、自然日、cohort。
- 验收流程：发版前检查关键事件。

> 💡 埋点质量不是数据同学一个人的事。商业化运营必须能说清“这个事件用于判断哪一个收入问题”。

## 11. 常见误区

1. **事件越多越安心。** 没有业务问题的事件只会增加维护成本。
2. **只埋成功，不埋失败。** 失败原因才是排障入口。
3. **只看广告展示，不看广告场景到达。** 无法判断展示少的真正原因。
4. **只埋 purchase_success。** 订阅收入由续费、退款、宽限期、恢复共同决定。
5. **没有 paywall_id。** 付费墙 A/B 上线后无法复盘。
6. **没有 experiment_exposed。** 业务事件无法按实验组切分。
7. **币种缺失。** 多国家收入无法正确汇总。
8. **没有去重键。** 广告收入、购买、回调会重复计算。
9. **忽视隐私状态。** 归因和广告收入差异会被误判为渠道问题。
10. **自然日和 cohort 混用。** 当天收入和某批用户 LTV 不是同一个问题。

## 附：一页速查表

```text
核心公式：
总收入 = IAA 收入 + IAP 收入
IAA 收入 = 展示次数 × eCPM / 1000
IAP LTV = 付费墙触达 × 购买/试用转化 × 续订留存 × 净单价
ROI = cohort LTV / cohort CAC

三条必建漏斗：
核心任务：app_open → task_start → task_complete → result_view → export_success
广告：ad_scene_enter → ad_request → ad_load_success → ad_show → ad_impression → ad_revenue
付费：paywall_show → package_click → purchase_start → purchase_success → entitlement_granted → renewal

必备公共属性：
user_id / install_id / app_version / platform / country / media_source / campaign / experiment_id / variant_id / event_time

必备收入属性：
monetization_type / value / currency / is_estimated / revenue_source / transaction_id or impression_id

诊断顺序：
总收入 → IAA/IAP → 漏斗节点 → 国家/渠道/平台/版本/实验 → 口径与延迟校验
```

# IAA 广告变现入门到精通 · 学习文档

> 面向工具/实用类 App（清理、计算器、扫描、转换、文件管理、VPN、桌面、天气等）的**应用内广告变现（In-App Advertising, IAA）**。
> 本文基于 `iaa-monetization-expert` skill 重新编排，把速查表变成一条可以顺着读下来的学习路径。
> 读完你应该能：看懂一张变现数据看板、设计一套广告位、配置聚合瀑布流、并在收益异常时定位到根因。

---

## 0. 一张图理解整个生意

工具 App 大多免费，靠广告赚钱。整个变现工作，本质上只在优化**一个公式**：

$$\text{广告收益} = \text{展示次数（impressions）} \times \frac{\text{eCPM}}{1000}$$

- **eCPM**（effective Cost Per Mille）= 每一千次展示带来的收益。它是变现健康度的**第一指标**。
- 公式只有两个杠杆：**做大展示次数** 或 **抬高 eCPM**。
- 但这两个杠杆都被一根隐形的绳子拽着——**留存和体验**。广告加得越猛，短期收益越高，用户流失越快，最终收益反而崩。

> 🧭 **贯穿全文的一句话**：变现不是"把广告塞满",而是在「收益」和「留存」之间找那条让 **LTV（用户终身价值）最大** 的线。

## 1. 把收益公式拆成一棵"收益树"

eCPM 和展示次数还能继续往下拆。把它们拆开，你才知道一个数字变化时该去**哪根树枝**找原因。这棵树是后面所有诊断的地基。

```
                          总收益
                            │
            ┌───────────────┴───────────────┐
           DAU                          人均收益（ARPU）
        (日活用户)                            │
                            ┌────────────────┴────────────────┐
                      人均展示次数                            eCPM
                            │                                  │
        ┌──────────┬────────┴────────┬──────────┐    ┌────────┴────────┐
     请求渗透率  人均请求PV        填充率      展示率  广告主出价  CTR×CVR
```

用公式串起来就是：

$$\text{总收益} = \text{DAU} \times \text{人均收益}$$
$$\text{人均收益（ARPU）} = \text{人均展示次数} \times \frac{\text{eCPM}}{1000}$$
$$\text{人均展示次数} = \text{请求渗透率} \times \text{人均请求PV} \times \text{填充率} \times \text{展示率}$$
$$\text{eCPM} = \text{广告主出价} \times \text{CTR} \times \text{CVR} \times 1000$$

### 左半棵：人均展示次数（"量"的链路）

每个用户能贡献多少次展示，由四个**串联的转化率**决定，任何一环掉了，整条都掉：

| 因子 | 含义 | 掉了通常是因为 |
|------|------|----------------|
| **广告请求渗透率** | 活跃用户里有多少真正发起了广告请求 | SDK 初始化失败、广告配置拉取失败、代码漏掉了广告逻辑 |
| **人均请求 PV** | 每个用户平均请求几次 | 频次设置、用户使用深度、自动请求/重试开关 |
| **填充率** | 请求里有多少返回了广告 | 底价太高、瀑布流太浅、网络宕机 |
| **展示率** | 填充的广告里有多少真的展示了 | 缓存过期、渲染失败、用户没走到广告场景、UI 遮挡 |

### 右半棵：eCPM（"价"的链路）

| 因子 | 你能控制吗 | 怎么影响 |
|------|-----------|----------|
| **广告主出价** | ❌ 间接 | 取决于平台预算池和竞争。**电商大促会冲高**（618、双 11、季度末预算冲刺），节后回落 |
| **CTR（点击率）** | ✅ 能 | 广告位置、时机、尺寸、视觉醒目度 |
| **CVR（转化率）** | ⚠️ 部分 | 主要靠平台，你能做的是让广告内容更可见、更易懂，缩短下载/安装路径 |

> 💡 **为什么要背这棵树？** 因为所有"收益掉了/涨了"的问题，最终都能落到某一片叶子上。诊断 = 自顶向下走这棵树，找到**那片动了的叶子**，再判断是前端（投放/买量）问题还是后端（产品/变现）问题。详见第 9 章。

## 2. 看懂数据：最容易错的一课——结算口径 vs 统计口径

**这是新手第一大坑，单独拎出来讲。**

每个聚合平台的数据看板，都有**两套并行的数据**。把它们混为一谈，是最常见的分析错误：

| 口径 | 来源 | 用途 | 注意 |
|------|------|------|------|
| **三方 API 数据**（指标名带 "API" 后缀：收益、eCPM API、展示 API） | 从每个广告网络的报表 API 拉取 | **结算口径**——所有"钱"的数字以它为准，能和网络自己的后台对上账 | **延迟**（通常次日、分批拉取）。需要给每个网络开通 Report-API 授权 |
| **SDK 统计数据**（不带 "API"：展示、点击、请求、填充率、DAU） | 聚合 SDK 自己在客户端埋点统计 | **实时**（约 5 分钟），用来做漏斗、人均、频次分析 | **只是估算**，永远不是结算数。预估收益用的是你手填的排序价格，floor 填得准它才准 |

**两条铁律：**
1. **对账只认带 API 的指标**（结算口径）。拿 SDK 统计的展示/预估收益去对账，必错。
2. **A/B 测试只看预估指标**（统计口径），因为 API 收益是整代码位汇总的、不按实验组拆分。

**展示 Gap（展示Gap）** = (SDK展示 − 展示API) / 展示API
- 因为两边的计数边界不同，**0–15% 属于正常**。
- **>15% 才需要排查**（先确认两边时区一致、API 拉取窗口已过）：
  - 展示 API > SDK 展示 → 有个老的/重复的三方代码位在你 SDK 之外偷跑（比如没接聚合的旧版本）。
  - 展示 API < SDK 展示 → 网络判定你统计的部分展示**无效**做了折损（如原生/banner 未满 1 秒或可见面积 <50%，开屏未覆盖 75% 屏幕）。

## 3. 关键指标速查（带健康区间）

把第 1 章的叶子配上"正常长什么样"，日常看板就是盯这些数偏没偏。

### 收益类
| 指标 | 公式 | 解读 |
|------|------|------|
| **eCPM** | 总收益 / 总展示 × 1000 | 跨网络的综合单价，健康度首要指标 |
| **ARPU** | 总收益 / 总用户 | 每用户变现效率 |
| **ARPUDAU** | 当日收益 / DAU | 每日每用户收益，**最可操作的口径**，A/B 测试的主指标 |
| **LTV** | ARPUDAU × 平均留存天数 | 每用户终身价值，所有取舍的最终裁判 |

### 交付类（工具 App 健康线）
| 指标 | 定义 | 健康区间 |
|------|------|----------|
| **填充率** | 填充 / 请求 | Tier 1 地区 ≥ 90% |
| **展示率** | 展示 / 填充 | ≥ 85%（加了预加载后降到 40–60% 也正常，见下） |
| **CTR** | 点击 / 展示 | Banner 0.5–3% / 插屏 3–10% / 激励 10–30% |
| **填充耗时** | 请求到填充的平均时间 | 视频 <10s，图片 <2s |

> ⚠️ **展示率警告**：太多"请求成功但不展示"的广告，会让广告平台判定你的**资源利用率低 → 给代码位降权 → 填充率和 eCPM 双双下降**。展示率不该长期 <10%。但**加了预加载后展示率掉到 40–60% 是正常且正向的**——提前缓存的广告未必都展示，别因此回滚预加载。

### 一眼看穿的指标关系（诊断捷径）
- eCPM 掉、展示稳 → 网络侧问题（季节性、竞价行为、广告质量）
- eCPM 掉、展示也掉 → 填充率问题（瀑布流配置、网络宕机）
- 展示涨、eCPM 掉 → 过度曝光稀释了竞价密度；或 banner 刷新太快（<30s）灌了一堆低价展示
- ARPUDAU 稳、DAU 涨 → 健康扩张 ✅
- ARPUDAU 降、DAU 涨 → 新用户质量下降或市场饱和 ⚠️

### 用户广告价值衰减（一个重要直觉）
> 用户进入 App 后，广告价值随时间/使用深度**衰减**。**第一个广告位、第一个激励视频位的 eCPM 通常最高**；靠后的广告位频次高但单价低。
> → **高价值广告位应前置**（靠近入口），低价值频次型广告位后置。

## 4. 四种广告形式：各自的定位

| 形式 | eCPM（Tier1） | 体验代价 | 工具 App 用法 | 关键纪律 |
|------|--------------|----------|---------------|----------|
| **Banner** 横幅 | 最低 $0.10–1.50 | 低（放对位置） | 计算器/转换器/文件列表底部 | 刷新 30–120s，越快展示越多但单价越低；精密操作页别放 |
| **Interstitial** 插屏（全屏） | 中 $2–8 | 高（时机错就很烦） | 扫描完/转换完/清理完 | **绝不放在 App 启动**（必卸载）；频次 1 次 / 3–5 分钟，每场景≤3–4 次 |
| **Rewarded** 激励视频 | 最高 $5–20 | 几乎为零（用户自愿） | 解锁额外次数、去水印、跳过等待 | 工具天然缺货币锚点，要**造合成价值**："看广告解锁今日 10 次额外转换" |
| **Native** 原生/信息流 | 中 $1–6 | 低（融合好时） | 内容流、推荐、天气列表 | 纯工具往往内容货架不足，原生跑不动 |

**按产品类型选形式：**
- 工具功能类 → **信息流 + 插屏**为主，植入主路径、不打断操作
- 游戏类 → 激励视频为主（跳过/复活/翻倍）
- 资讯类 → 信息流 + 插屏
- 网赚类 → 多种组合 + 激励视频（翻倍奖励）

**频次哲学**：短平快高回收产品 → 广告前置、高频；长留体验产品 → 广告后置、低频。

## 5. 变现核心机制：瀑布流 vs 竞价 vs 混合

广告从哪个网络出、以什么价出，由**聚合（mediation）**机制决定。这是变现里最"技术"的一块。

### 5.1 瀑布流（Waterfall）
按预估 eCPM 把网络**排成一个有序列表**，请求从高到低逐层下探，直到填充。

- **优点**：完全掌控优先级、行为可预测。
- **缺点**：每跳一层有 50–200ms 延迟；底价要手动维护；可能次优（最高出价者排在一个不填充的网络下面）。

**配置经验值：**
- 底价设在近 7 天均值的 **80–90%**（底价越高填充越低，且交付 eCPM 往往贴着底价走）
- 相邻层价格差 ~20%
- 合理分层在 **10–20 层**（按 DAU 体量：T1 地区 30–40 层，T2 20–30，T3 10–20）
- 每周复查底价

**瀑布流结构参考：**
| 区域 | 配置 | 层数 | 要点 |
|------|------|------|------|
| 竞价池（并行层） | A/B/C/D-bid | 2–4 | **绝不设竞价底价**——会拖垮竞价填充 |
| 头部高底价 | 单网络高 floor（如 $80） | 2–4 | 最大化单价 |
| 中部中底价 | 多网络降序交叉排（$70→$20） | 2–8 | 填补价格断层 |
| 尾部低/无底价 | 低 floor + 无 floor 兜底 | 2–6 | 无底价自动价保填充 |

**分层纪律：**
- 整体填充 ≥ 90%，每层填充 ≥ 1%（最好 ≥ 5%）；接近 0 的顶层可砍掉
- 看每层**收益占比 vs 展示占比**：若某 $5 层吃了 30% 展示却只贡献 10% 收益 → 限频或削薄它,加高价层（精细化分层）
- 新 App 无历史 → 先跑 "$50→无底价、步长 ~$10" 的粗瀑布 2–3 天（每层攒够 ≥2000 展示，竞价模型才稳）再调
- **开屏是例外：瀑布流 ≤ 5 层**,否则慢加载会错过展示窗口

### 5.2 排序价格 vs 底价（SDK 侧聚合的关键概念）
> 在 TopOn 这类 SDK 侧聚合里，控制台填的**排序价格（排序价格）只决定请求/展示的优先级排序，不卡填充**。真正的价格底价在网络自己的后台。

- 有网络后台 floor 权限 → 排序价格 = 后台 floor，预估收益/LTV 才准
- 无 floor 权限 → 排序价格只决定顺序，填个真实估计值 + 开**自动价格**
- **自动价格**：聚合用该源近 7 天均值 eCPM 当排序价格，需 Report-API + 累计 ≥2000 展示才生效，适合低/无底价尾层

### 5.3 实时竞价（In-App Bidding / Header Bidding）
所有网络**同时出价**，最高者赢。

- **优点**：零瀑布延迟、最优清算价、配置更简单、能知道每次展示的价值。
- **缺点**：需网络支持竞价（不是都支持）；控制力弱；部分网络竞价时压价、瀑布流里反而表现好。
- **国内现状**：RTB 推广缓慢，受限于各平台竞价协议和数据互通。

> ⚠️ **竞价底价警告**：设竞价底价会过滤掉低于底价的竞胜 → **直接拉低竞价填充和收益**。**爬坡期不设底价，稳定后再尝试。**

**S2S vs C2S**（服务端 vs 客户端竞价）：对放置策略透明（接对 SDK 版本即可），但 debug 时要分清——S2S 在服务端解析（Meta、AdMob、Mintegral、Pangle、Unity 等），C2S 在端上解析（Chartboost、Huawei、TapTap 等）。

### 5.4 混合模式（推荐默认）
竞价实例放并行池，瀑布流当兜底尾巴：

```
[竞价池: AdMob | FAN | AppLovin | Pangle]
      ↓ (没填充)
[瀑布流: ironSource | Unity | Mintegral]
      ↓
[自家广告 / 无填充兜底]
```

- 所有支持竞价的网络都丢进竞价池
- 瀑布流尾巴：1–3 个不支持竞价的网络
- 监控：竞价池填充率 <85% → 尾巴太浅，加网络

### 5.5 聚合控制台的几个实用杠杆
- **并行请求（并行请求）**：一次发 N 个源、降填充延迟。但只影响**请求**不影响展示顺序;**推荐 2–3，绝不超过 5**——请求多展示少会被平台判定资源利用率低而降权。
- **兜底广告（兜底广告）**：与瀑布流**并行**（不是之后）跑一个无底价源,瀑布流没填它顶上。提升整体填充、缩短延迟，但不保证 100% 填充。
- **流量分组（流量分组）**：把用户按 geo/城市/网络/版本/渠道/用户价值等切组，每组一套瀑布流——精细化变现的核心。**优先级高的组先匹配**（"美国"组要排在"美洲"组之上）;**默认分组是兜底,永远别关、永远配有效广告位**,否则未命中流量全丢。
- **展示频次控制**：代码位级 + 广告源级，各有时/日上限和间隔秒数。既是没有 floor 时的质量杠杆,也是上线期的政策安全阀（Meta/AdMob 量小时几台异常设备就可能封号 → 上线期给这俩设每源 ~10 次上限）。

## 6. 主流广告网络与聚合平台

### 全球 Tier 1（高填充 + 高 eCPM）
| 网络 | 强项 | 弱点 | 最佳地区 |
|------|------|------|----------|
| **Google AdMob** | 需求池最大、自带聚合 | 部分场景 eCPM 不如垂直网络 | 全球 |
| **Meta Audience Network** | FB 识别用户上 eCPM 高 | 政策重，iOS ATT 削减库存 | 美、欧 |
| **Pangle（字节）** | TikTok 重镇市场强势 | 亚洲/中东/拉美外有限 | 东南亚、印度、中东 |
| **Unity Ads** | 激励视频强 | 偏游戏需求，工具填充弱 | 全球 |
| **ironSource** | 聚合 + 自有需求强 | 单独用不如走聚合 | 全球 |
| **AppLovin** | MAX 竞价架构 + AXON 2.0 AI 引擎 | 需求偏游戏 | 美、欧 |

### 国内市场
| 网络 | 归属 | 强项 |
|------|------|------|
| **穿山甲（CSJ）** | 字节 | 国内最大联盟，填充和 eCPM 领先，**国内变现首选** |
| **优量汇（YLH）** | 腾讯 | 依托微信/QQ，游戏类/网赚类好 |
| **快手广告** | 快手 | 下沉市场覆盖好 |
| **百度联盟** | 百度 | 搜索类流量补充，弱于前三 |

**选网络心法：** AdMob + 匹配 top-3 地区的 2–3 个网络起步（国内：穿山甲 + 优量汇）→ 逐个加、量增量提升 → 30 天后贡献 <3% 的砍掉 → 一次接入通常 5–8 个网络够用，>7 个很少有边际价值还增 SDK 体积。

### 聚合平台举例：TopOn
一个**聚合/中间层平台**（不是需求网络），一个 SDK 接 40+ 全球和国内网络。核心控制台杠杆就是第 5 章那些（排序价格/自动价格/并行请求/兜底/流量分组/频次/同价展示权重）。自带 **TopOn ADX** 需求源（开关即用，无需单独 SDK 或发版）。还提供漏斗分析、留存/LTV、用户行为、分小时、数据预警、A/B、交叉推广 + 直投等控制台工具。

## 7. 工具 App 的广告位设计

### 按 App 类型的放置建议
| App 类型 | 主广告位 | 次广告位 | 避免 |
|----------|----------|----------|------|
| 清理/优化 | 清理后插屏 | 结果页 banner | 扫描中插屏 |
| 文件管理 | 文件列表 banner | 复制/移动完成插屏 | 文件操作中插屏 |
| 计算器 | 底部 banner | "="后插屏 | 挡输入的插屏 |
| 转换器 | 转换后插屏 | 结果页 banner | 遮输出的 banner |
| 扫描/二维码 | 扫描后插屏 | 历史页 banner | 开相机前插屏 |
| VPN | 高级服务器激励 | 断开时插屏 | VPN 运行中的广告 |
| 天气 | 预报页 banner | 时/天列表原生 | App 打开时插屏 |

### 放置设计七原则
1. **任务完成边界**：插屏放在用户目标**达成后**，绝不在追求目标的过程中
2. **可预测**：让用户学会广告出现在哪，随机放置增烦躁、增流失
3. **最小交互距离**：一个广告后,留 ≥30 秒或 ≥3 次交互再出下一个
4. **首次会话克制**：首场会话插屏限 0–1 个（首场对留存最关键）
5. **退出意图广告**：按返回时出广告能赚流失用户的钱但加速流失——高留存工具应避免
6. **激励位必须有真价值**：解锁的东西用户不想要,完成率趋近 0
7. **主路径渗透**：在用户主路径上植入广告才能有效提升展示率

### 广告位数量
- <5 屏：1–2 个；5–10 屏：2–4 个；>10 屏：不超过 ⌈屏数/3⌉
- 每加一个广告位都会稀释单位展示，因限频和刷新机制拉低单位 eCPM

## 8. 地区优化（Geo）

不同地区 eCPM 差 10–30 倍，**全球平均 eCPM 是没意义的数字**,必须分地区看。

| Tier | 代表地区 | 插屏 eCPM | 策略 |
|------|----------|-----------|------|
| **Tier 1** | 美/加/澳/英/德/日/韩等 | $3–10 | **最大化 eCPM**：竞价、激励等高端形式、多网络竞争 |
| **Tier 2** | 法/意/西/新/港/台等 | $1–4 | **最大化填充**：混合聚合、3–4 网络、收紧底价 |
| **Tier 3** | 巴/墨/土/俄/马/泰等 | $0.30–1.50 | **最大化展示**：放宽频次、低底价、奖励行为 |
| **Tier 4** | 印/印尼/菲/尼/巴基等 | $0.05–0.30 | **生存**：靠展示量,激励视频提人均收益,插屏易致流失 |

**铁律：同一广告位、不同地区 = 不同瀑布流。** 给 Tier 1 用户发 Tier 4 的瀑布流,每次展示损失 10–30 倍收益。没有 geo 数据 = 白白挨这刀。

## 9. 诊断手册：数据出问题怎么查

这是把第 1 章"收益树"用起来的地方。两大工具：**漏斗分析**（找量的漏点）+ **收益分解**（找是哪片叶子动了）。

### 9.1 漏斗分析（最可操作的诊断）
每次展示都走一条有序链路,相邻节点的转化率能**精确定位用户/收益在哪漏**。务必**分广告位**、**按人均次数**看（汇总平均会掩盖问题）。

```
应用启动 → 获取策略 → 流量请求 → 流量填充 → 到达广告场景 → 触发展示 → 展示 → 点击
         策略到达率   　       填充率  　       Ready率　       展示成功率   点击率
```

| 漏点 | 可能原因 | 修复 |
|------|----------|------|
| 获取策略 < 应用启动 | SDK 初始化/配置拉取在部分会话失败 | 在可靠入口加预加载，考虑全自动加载 |
| 填充率低 | 瀑布流太浅 / 底价太高 / 网络宕机 | 加无底价兜底层，查各源报错日志 |
| Ready 率低但填充高 | 用户到场景时广告还没预加载好 | 在场景合适时机预加载（别太早,见衰减） |
| 场景到达率低 | 广告入口埋太深 | 把广告场景往主路径移 |
| 展示成功率低 | 缓存过期 / 渲染失败 / 集成 bug | 查报错日志、缓存有效期、UI 遮挡 |

**诊断恒等式**：人均展示次数 = 人均请求次数 × 填充率 × 展示率。人均展示一动,必然落在这三个率之一,追那个动了的。

### 9.2 收益分解：自顶向下走收益树
> 总收益 = 人均收益 × DAU；人均收益 = 人均展示次数 × eCPM / 1000；人均展示次数 = 人均请求次数 × 填充率 × 展示率。

逐叶子排查,每片叶子都要分**前端（投放/买量侧）**和**后端（产品/变现侧）**两面：

| 动的叶子 | 前端排查 | 后端排查 |
|----------|----------|----------|
| **DAU** | 买量降、自然量降、流失升 | — |
| **人均请求次数** | 用户质量/意愿变化 | 改了频次/场景?动了自动请求/重试?增删了广告位? |
| **填充率** | 用户质量降→网络少竞价/填充 | 抬了底价?撤了兜底层?某源被限/封?季节预算(节后跌/大促涨)? |
| **展示率** | 弱网/低端机用户变多 | 收紧了超时?加了预加载(正常下降)?并行请求太多缓存了未展示广告? |
| **eCPM** | 新用户构成、geo 构成、用户质量 | 底价变动?单网络还是全网络动?总展示量摆动稀释竞价密度? |

**总规则**：前端问题要买量侧修,后端问题要变现/产品侧修。**永远按版本拆开**排除发版回归——如果所有渠道在同一版本上都掉,那就是版本问题。

### 9.3 几个反直觉的洞察（避免误判为 bug）
- **低价源比高价源展示还多 = 正常**：展示数取决于 **填充率 × eCPM,不是 eCPM 单独**。$1000/1% 填充的源 100 次请求才赢 1 次,$1/100% 填充的源吃掉其余 99 次。按**收益贡献**而非展示占比评判每层。
- **竞价胜率高但展示率低 = 正常**：竞价"赢得拍卖"和"实际展示"是两个阶段,赢了之后若更高价的瀑布层先填充,它就不展示。要和**同价位的普通瀑布层**比展示率,别跟别的网络或差很远的价位比。

### 9.4 误点（误点）分析
有些产品故意设计高误点提 CTR → 提 eCPM。**实际效果有限且风险大：**
- CTR 升 + CVR 不降 → eCPM 才可能升；CTR 升 + CVR 同比降 → eCPM 不变；CVR 降更多 → eCPM 反降
- 频繁误点 → 体验差 → 留存降 → LTV 降
- **结论：谨慎用,收益增量通常被留存损失抵消。**

## 10. eCPM 优化的三个可控节点（穿山甲方法论）

收益公式完整展开后,三个可控转化节点是优化抓手：

$$\text{收益} = \text{请求} \times \text{填充率} \times \underbrace{\text{展示率}}_{节点一} \times \underbrace{\text{点击率}}_{节点二} \times \underbrace{\text{转化率}}_{节点三} \times \text{出价}$$

**节点一 · 展示率**（让每次填充变成有效展示）
1. 提高广告位可见度——位置越靠近入口展示率越高,深层页面广告几乎触达不到
2. 预加载缓存消除实时延迟,视频尤其关键。**但时机不是越早越好**：预加载后用户没触发 → 展示率降 → 系统判流量价值低 → 影响填充。首页签到位→启动时加载;结算页→开始游戏后加载;深层页→靠近时加载
3. 注意广告有效期(穿山甲：开屏 3 小时,其他 1 小时),过期展示被系统过滤为无效

**节点二 · 点击率**（扩大尺寸和点击区域,但不靠误点）
1. 广告元素正确完整显示(icon/标题/描述/图片/logo/广告标识)→ 用户获取完整信息 → 有效点击
2. 合理扩大尺寸(在 CTR 提升和不侵占内容影响留存间平衡)
3. 每个元素可点击,扩大点击区域

**节点三 · 转化率**（缩短点击到下载/安装的路径）
1. SDK 初始化设置允许直接下载的网络(WiFi + 4G/5G)
2. **下载完成自动弹安装提示**——穿山甲数据：可提升转化率 **3 倍以上**,性价比最高的手段
3. 用"使用创意区域",点击直接下载、无需跳网页再点
4. 确保跳转链路通畅(iOS 跳 App Store / Android 开始下载)

## 11. A/B 测试

- **可测变量**：插屏频次、放置时机、形式组合、各 geo/形式底价、瀑布流排序、banner 刷新率、并行请求数、流量分组配置、兜底层开关……
- **测试设计**：
  - 时长：最少 7 天,14 天更稳
  - 样本：每组最少 **5 万 DAU**(eCPM 高方差,样本不足易假阳性)
  - 主指标：**ARPUDAU**(不是单看 eCPM——eCPM 能涨但展示崩)
  - 护栏：卸载率相对上升 >5% 自动判负
- **决策示例**：
  ```
  A(对照): 频次 1/5min, ARPUDAU $0.012, D7 留存 38%
  B(测试): 频次 1/3min, ARPUDAU $0.018, D7 留存 35%
  → 收益 +50%,留存 -3pp。算 LTV：ship 当且仅当 LTV_B > LTV_A
  ```
- **聚合平台的坑**：
  - **只看预估指标**,API 收益不按实验组拆分
  - 设备分配是**粘性**的(改分流比例会重新随机)
  - 单代码位结果和大盘打架时,用 **AABB**(两对照两测试)验证分流是否均匀
  - **辛普森悖论**：多代码位放一个实验时,各代码位的赢家可能和汇总赢家相反——逐个代码位挑最优,再用独立实验复验

## 12. 隐私与合规（直接影响 eCPM）

| 法规 | 影响 |
|------|------|
| **iOS ATT** | 2025 年 IDFA 可用率 30–50%；无 IDFA 时受影响用户 eCPM 降 15–40%。SKAdNetwork 转化值管理能挽回部分归因,但不直接恢复 eCPM |
| **GDPR / CCPA** | 欧盟/加州需 CMP 同意管理；未同意用户只能非个性化广告,eCPM 约为个性化的 50–70%；欧盟需 IAB TCF 2.2 |
| **COPPA / 儿童向** | 仅儿童安全库存,网络严重受限,eCPM 降 60–80%。"通用但儿童会用"应做年龄门而非打 COPPA 标 |

## 13. 二十条常见陷阱（速查清单）

1. **孤立地盯 eCPM**——eCPM × 展示量 = 收益,靠减展示抬 eCPM 往往总收益更少,务必同看 ARPUDAU
2. **瀑布流配置漂移**——半年前的底价已过期,每周复查是底线
3. **网络太多**——SDK 膨胀、增崩溃,每个网络应贡献 ≥5% 收益
4. **忽视 geo 分布**——Tier 4 安装激增会被误读成 eCPM 崩盘
5. **首次启动放插屏**——D1 留存损失几乎总是超过那次展示的收益
6. **不做频次限制**——短期收益尖峰后留存崩、再收益崩
7. **激励位无价值**——"白看广告"完成率 0%
8. **刷新太快**——banner <30s 刷新,广告主识别后压价,净 eCPM 反降
9. **样本不足就下结论**——<5 万 DAU/组常出假阳性
10. **不分平台**——iOS 和 Android 的 eCPM/ATT/网络表现都不同
11. **盯广告重复率却无解法**——根因是源单一或间隔太短,解法是多源或拉大间隔
12. **ARPU 降只查后端不查前端**——可能是投放端用户构成变化,需分版本对比
13. **忽视展示率**——高填充低展示 → 平台降权 → 填充和 eCPM 双降
14. **假设广告位价值均等**——首位和首激励位价值最高,高价值应前置
15. **把开屏 eCPM 当可深调指标**——它主要反映用户质量,杠杆在投放端筛用户
16. **混淆结算口径与统计口径**——带 API 才是结算口径,展示 Gap 15% 内正常
17. **关闭/不配默认流量分组**——默认分组是兜底,关了 = 直接丢量
18. **过早设竞价底价**——会过滤竞胜拉低填充,爬坡期不设、稳定后再试
19. **并行请求设太多**——只影响请求不影响展示,2–3 条最多 5 条
20. **预加载后展示率降就回滚**——降到 40–60% 正常且正向,别回滚

## 附:核心公式一页纸

```
总收益          = DAU × 人均收益
人均收益(ARPU)  = 人均展示次数 × eCPM / 1000
人均展示次数    = 请求渗透率 × 人均请求PV × 填充率 × 展示率
eCPM            = 广告主出价 × CTR × CVR × 1000
LTV             = ARPUDAU × 平均留存天数
展示Gap         = (SDK展示 − 展示API) / 展示API    (>15% 排查)
诊断恒等式      = 人均展示次数 = 人均请求次数 × 填充率 × 展示率
```

> **一句话收尾**：所有优化都在「收益」和「留存」之间求 LTV 最大；所有诊断都是自顶向下走收益树,找到那片动了的叶子,再分前端/后端对症下药。

## 0. 一句话理解

IAA（In-App Advertising）变现的本质：把**用户会到达的广告机会**，以尽量高的价格、尽量高的售卖成功率、尽量低的体验损伤，卖出去。

```text
广告收入   = 展示次数 × eCPM / 1000
ARPDAU     = 人均展示次数 × eCPM / 1000
人均展示次数 = 广告请求渗透率 × 人均请求 PV × 填充率 × 展示率
```

> 🧭 **贯穿全文的一句话**：IAA 的诊断主线永远是"人均展示次数 × eCPM"这棵收益树——先判断是**量**出了问题还是**价**出了问题，再一路拆到具体叶子。笼统说"今天 eCPM 掉了"无法定位根因。

**为什么必须先分"量/价"？** 因为这两支的修复动作几乎不重叠：量的问题改的是产品路径、请求时机、填充兜底（产品/客户端/聚合的活）；价的问题动的是用户质量、样式位置、买量结构（运营/投放的活）。不先分流，就会出现"运营在调底价、其实是产品把广告位埋深了"这种各修各的、谁都没修对的局面。

> 🧪 **自测**：收入环比掉了 15%，你问的第一个问题应该是什么？（答案在本章 🧭：先看是 DAU/ARPDAU 哪个掉，即量还是价。）

## 1. 主脊柱：把收入拆成一棵可运营的收益树

```text
广告收入
├─ DAU
└─ ARPDAU
   ├─ 人均展示次数
   │  ├─ 广告请求渗透率   有多少活跃用户走到了"会发请求"的路径
   │  ├─ 人均请求 PV      这些用户平均触发了多少次可售卖机会
   │  ├─ 填充率          发出的请求里，多少拿到了广告
   │  └─ 展示率          拿到广告后，多少真正展示成功
   └─ eCPM
      ├─ 广告主出价
      ├─ 点击率 CTR / 转化率 CVR
      ├─ 地区 / 渠道 / 用户质量
      └─ 广告样式与展示位置
```

穿山甲把收益写成另一种等价形式 [[4]](https://www.csjplatform.com/growthcenter/6101274400195d0046c2731d)：`收益 = 广告请求 × 填充率 × 展示率 × 点击率 × 转化率 × 广告主出价`。两个公式是一回事——前者是**业务看板视角**，后者是**广告转化漏斗视角**。

**为什么这棵树比"盯大盘收入"强？** 机制在于它把一个**结果指标**改写成了一串**可操作叶子**，而每个叶子都对应一个明确的责任人和动作。结果指标只能告诉你"病了"，叶子才告诉你"病灶在哪、谁去治"。

**示意算例 + 反事实（量 vs 价谁更重要）：**

```text
方案 A：人均展示 4 次，eCPM 20 → ARPDAU = 4 × 20 / 1000 = 0.080
方案 B：人均展示 2 次，eCPM 35 → ARPDAU = 2 × 35 / 1000 = 0.070
```

B 单价高 75%，人均收入却更低。**反事实**：要让"抬价"不亏，量的下降幅度必须小于价的上升幅度——这里价 ×1.75、量 ×0.5，乘积 0.875 < 1，所以亏。若 B 的展示只掉到 3 次（×0.75），则 3×35/1000=0.105 > 0.08，抬价才划算。**这就是 IAA 最常见的误判**：把"价格高"当成"收入高"，真正要最大化的是 ARPDAU/LTV，不是把 eCPM 顶到最高。

> 🧪 **自测**：某位置把底价抬高使 eCPM +20%，但填充导致展示 -25%，收入涨还是跌？（提示：1.2 × 0.75 = 0.9，跌 10%。）

## 2. 头号坑：只看 eCPM，不看售卖率、展示率和体验

只记一个新手误区，就记这个。广告收益取决于两个核心量：**售卖价格**（eCPM）× **售卖成功率**（填充率 × 展示率）。

**机制：为什么"高底价"和"猛加广告位"都会反噬？**

- **抬底价反噬**：底价提高 → 高价层更难被填满 → 填充下降 → 展示次数变少。当"少掉的展示量 × 原单价"> "多卖的价差 × 仍成交的展示"，总收入下降。底价不是越高越好，是有一个让 `填充 × 单价` 乘积最大的点。
- **加广告位反噬**：频次过高伤两层——**短期**误点/厌烦/快速跳过拉低 CTR/CVR（平台据此判定流量质量下降，回给更差的广告）；**中长期**用户更快流失，未来广告机会总量（DAU × 人均请求）下降。

> 💡 IAA 的本质是平衡"当前展示价值"和"用户未来还能回来几次"。变现方案必须和留存一起看——它们是同一个问题的两面，不是两件事。

> 🧪 **自测**：为什么"理论 eCPM 很高"的配置，实际收入可能很差？（答案：高底价压低了填充与展示，卖不出去的高价等于 0。）

## 3. 广告样式：按用户场景选，不按单价想象选

AdMob 把常见格式定义为 Banner、Interstitial、Rewarded、Native、App Open 等 [[1]](https://support.google.com/admob/answer/6128738?hl=en)。选样式的标准只有一条：

> 🧭 **哪个最匹配该场景下用户的注意力和容忍度** —— 单价高必须和场景匹配并行考虑，不能单看单价。

| 样式 | 典型工具场景 | 最关键的运营问题 |
|---|---|---|
| 开屏 / App Open | 启动页、热启动回前台 | 不拖慢进入；要有首屏兜底 |
| Banner | 主页、结果页底部、列表底部 | 不遮挡主操作；保持可见性 |
| 插屏 | 功能完成页、页面切换、退出前 | 只放自然断点，别打断操作中 |
| 激励视频 | 解锁权益、额外次数、去水印、导出加成 | 奖励必须真有价值 |
| 原生 | 信息流、推荐列表、结果页卡片 | 元素完整、标识清晰、不伪装成内容 |

（以上样式的官方定义均见 AdMob 格式文档 [[1]](https://support.google.com/admob/answer/6128738?hl=en)；**注意**：源角标放在表外正文，不放进表格单元格——飞书/Notion 导入会丢掉单元格内的链接。）

**按用户任务把页面分三类**，广告友好度递增：进入前（适合开屏，但要快）< 任务中（最危险，尽量不打断）< 任务后（最稳，适合插屏/激励/原生）。

> 💡 工具产品的高质量广告位，往往在"用户刚完成一个小目标、愿意停一秒"的位置——不一定最显眼，但一定最自然。

**激励视频为什么常被高估又做坏？** 机制：它的收益来自用户**主动**观看（抵触小、完播高），所以杠杆不在"按钮放哪"，而在**奖励是否真解决用户当下需求**。工具用户对"立即生效的功能权益"（一次高清导出、解锁模板、+1 次识别、去一次水印）的感知，远强于"送 100 金币"这类游戏式抽象奖励。奖励不值钱 → 触发率低 → 这条高价样式形同虚设。

> 🧪 **自测**：同样是激励视频，A 产品奖励"金币"、B 产品奖励"本次免费去水印"，为什么 B 的触发率通常高得多？

## 4. 广告位设计：本质是用户路径经营

把广告位设计理解成"这里插个 ID"是过度技术化。真正的设计从**用户路径**出发：先理解核心功能与主路径 → 画出主流程和自然断点 → 参考同类产品 → 决定什么位置配什么样式 → 最后设计频次/顺序/兜底/异常回调。

**一个实用框架——把路径分成 4 种广告机会：**

```text
A 启动机会：刚进入，注意力集中但容忍度低   → 开屏（要快）
B 等待机会：在等结果 / 等跳转 / 等结束     → 插屏 / 原生
C 完成机会：刚做完一个动作                 → 插屏 / 推荐 / 激励（最佳）
D 欲望机会：想要更多权益                   → 激励视频（最佳）
```

**怎么判断一个广告位"埋深了"？** 信号：页面层级太深走不到、只有很小比例用户触发、到达也停留极短、位置在视觉角落、触发前置动作太多。穿山甲指出一、二级页面通常比三、四级更容易获得展示机会；要在浅层做激励入口，可用首页宝箱/签到/权益入口把广告机会前置 [[4]](https://www.csjplatform.com/growthcenter/6101274400195d0046c2731d)。

> ⚠️ 很多"填充低""收入低"不是平台问题，而是广告位根本没有足够用户到达。**先看场景到达率，再怀疑平台**——这也是机制级 why：到达率是收益树最上游的乘数，它若塌，下游再优化都是乘以一个小数。

> 🧪 **自测**：一个埋在四级页、只有 3% 用户触达的激励位，"填充率正常但收入极低"，根因更可能在哪一格？（提示：收益树最上游的渗透率/到达率。）

## 5. 售卖方式：单一广告源 / 聚合 / 竞价分别解决什么

对多数工具团队，重点不在自建销售，而在**多广告源管理**。

- **单一广告源**：接入简单、口径单纯、定位直接；但对单平台预算依赖大，某国家/机型/时段一旦没量填充就抖，议价与兜底空间小。
- **聚合（Mediation）**：AdMob 定义为让 App 从多个来源（AdMob Network、第三方网络、AdMob campaigns）投放，前提是每个网络正确接入配置 [[2]](https://support.google.com/admob/answer/9469204?hl=en)。MAX 把自己定位成可同时接 bidding 与传统网络的中介层 [[3]](https://support.applovin.com/en/max/getting-started)。**机制上聚合解决 3 件事**：① 让更多需求方竞争同一次展示；② 单平台预算波动时兜底填充；③ 让排序/分层/分组变成可调策略。
- **代价**：聚合给的不是"白送的更高收益"，而是"更高上限 + 更高管理复杂度"——多 SDK、多账号/ID/报表 API、要懂 waterfall/bidding/hybrid、要区分 SDK/API/预估/结算四套数，还要处理展示 GAP、时区、缓存回调。

> 💡 聚合的价值是"接得进、调得动、看得清"。看不清数据口径的聚合，只会让团队更混乱。

> 🧪 **自测**：团队刚上聚合，收入没涨反而争论变多。最可能缺的是哪一项能力——接入、调优、还是数据口径？

## 6. 漏斗诊断：所有排查都先回到这条链路

收益树告诉你"哪根枝杈病了"，漏斗报表告诉你"具体断在链路哪一段"。TopOn 把基础链路扩成运营漏斗 [[5]](https://help.toponad.net/cn/docs/qlHqYM)：

```text
应用启动/SDK 初始化 → 获取策略 → 请求广告 → 填充 → 到达广告场景
→ 广告 Ready → 触发展示 → 展示成功 → 点击/转化
```

**一张诊断地图（掉点 → 更可能的根因 → 第一动作）：**

| 漏斗掉点 | 更可能是什么 | 第一动作 |
|---|---|---|
| 获取策略低 | SDK 初始化 / 拉策略不稳 | 查初始化与配置拉取日志 |
| 请求低 | 没走到场景 / 代码没发请求 / 频控过严 | 回看触发路径与触发条件 |
| 填充低 | 底价高 / 广告源少 / 平台预算波动 / 用户质量差 | 看平台·国家·广告源分布 |
| Ready 低 | 请求太晚 / 缓存失效 / 没预加载 | 调预加载时机与缓存 |
| 触发低 | 激励不够 / 入口太深 | 改入口与触发文案 |
| 展示低 | show 失败 / viewability 不够 / 素材遮挡 | 查展示回调与 UI 可见性 |
| 点击低 | 样式弱 / 元素不可点 / 尺寸小 | 优化创意承载区域 |

**机制：为什么诊断要"先上游、后下游"？** 因为漏斗是连乘的——下游指标差，很多时候只是上游某一格塌了之后传导下来的结果。先修下游，等于在一个已经变小的基数上做优化，事倍功半。

**两个值得背下来的复合判断**（来自 TopOn 漏斗 [[5]](https://help.toponad.net/cn/docs/qlHqYM)）：

- **填充高、Ready 低** → 多半请求太晚，用户到场景时还没准备好 → 调预加载时机。
- **填充低、Ready 也低** → 更像 waterfall 配置本身有问题 → 查分层与底价。

> 🧪 **自测**：填充率 90% 但 Ready 率只有 40%，你先动预加载时机还是先动底价？（提示：填充高排除了"没广告"，问题在"广告来得太晚"。）

## 7. 并行 / 瀑布流 / 竞价：三种调度逻辑差在哪

这是最容易"词懂了、实战没懂"的一章。一句话定位它们各自**优先解决**的问题：

- **并行请求 → 优先解决"有没有广告可卖"**：同时请求多家、按比例展示。填充稳、响应快、对冷启动位置友好；代价是可能"请求多、展示少"，伤广告使用率，并行过多还浪费带宽、拉低平台对资源利用率的判断。
- **瀑布流 Waterfall → 优先解决"能不能卖得更贵"**：用 eCPM 底价把广告源分层，从高价层往下落（高价→中价→低价→兜底）。满足运营的控制欲（谁先请求、按国家/机型/广告位单独调价）；代价是链路更长、分层多则更慢、底价高则掉填充、维护重。内部"比较合理在 10–20 层"属团队经验口径、**非行业硬阈值**（以自己网络/国家结构/广告位实测为准）。
- **竞价 Bidding → 优先解决"谁真的愿为这次展示出最高价"**：多平台同时实时公平出价，替代你手动预测"谁大概更值钱"的瀑布分层，避免低顺位平台的优质 offer 被错过。MAX 支持 bidding 与传统连接并存 [[3]](https://support.applovin.com/en/max/getting-started)。

**实战最常见是 Hybrid**：`Bidding 池实时抬价 + Waterfall 兜底补填充`。

> ⚠️ 新团队最容易犯的错：基础链路还没稳，就急着上复杂调度。**先把请求、Ready、展示、口径、API 拉通，再谈排序优化**——否则复杂度只会放大本就存在的问题。

> 🧪 **自测**：用一句话分别说出并行、瀑布、竞价"优先"解决的那一个问题。

## 8. 预加载 / 缓存 / 兜底：很多"收入问题"其实是工程问题

运营本能会把收入问题归到"平台没量""底价没配好"，但 MAX/TopOn/穿山甲都在强调：**很多问题卡在加载与展示工程上**。

**预加载解决什么？** 让用户走到场景时广告已 Ready，无需现加载现等（视频文件大、加载慢尤甚）。但穿山甲提醒：预加载**不是越早越好**——若长期加载成功却不展示，会影响系统对该流量价值的判断 [[4]](https://www.csjplatform.com/growthcenter/6101274400195d0046c2731d)。这是一个**时机平衡**：太晚来不及 Ready，太早缓存过期/请求浪费/使用率下降。

内部自建逻辑的可学之处是**思路而非具体数值**：有缓存池（不裸请求）、失败顺延+重试、展示后立刻补货、兜底层不让场景空转。（其中"8s 超时、30s 下一轮、每策略缓存 2 条、缓存半小时、连续失败 6 次跳过"等是**当前团队实现口径**，非通用基准。）

MAX 入门最佳实践 [[3]](https://support.applovin.com/en/max/getting-started)：App 一启动就初始化 SDK、插屏/激励初始化后即开始加载、失败做指数退避、用户关闭后立刻加载下一条、Banner 持续在屏避免 viewability 失效。**本质都是同一目标**：不要让"本来能卖掉的曝光"因为准备得不够早而错过。

> 🧪 **自测**：把激励视频的预加载从"进入页面才加载"改成"上一页就预加载"，最可能改善漏斗哪一格？（答案：Ready 率。）

## 9. 数据口径：结算 / SDK / 预估，千万别混着看

第二个高频且致命的坑。TopOn 把数据分两大类 [[6]](https://help.toponad.net/cn/docs/Z4zsF6)：**三方 API 数据**（平台 API、需授权、更接近结算）vs **SDK 统计数据**（SDK 埋点、用于过程监控与排障、≠ 最终结算）。

```text
对账 / 收益确认 → 看三方平台后台或 API 数据
漏斗 / 排障 / 实时过程 → 看 SDK 统计数据
```

**机制：两者为什么一定有差？** 因为统计的不是同一件事——SDK 记的是"我收到了展示成功回调"，API 记的是"平台认定这次曝光最终有效并计入报表"，中间还有时延、时区、丢包、无效展示过滤 [[5]](https://help.toponad.net/cn/docs/qlHqYM)[[6]](https://help.toponad.net/cn/docs/Z4zsF6)。

必须区分的名词 [[6]](https://help.toponad.net/cn/docs/Z4zsF6)：展示（SDK 回调次数）、展示 API（平台报表口径）、eCPM（收益÷SDK 展示）、eCPM API（收益÷展示 API）、预估收益（按排序价/竞价价/历史价推算的过程值）。

**反事实算例**：某位置 SDK 展示 10 万、预估 eCPM 30，你以为今天进账 3000 元。但平台 API 显示有效展示只有 8 万、结算 eCPM 25 → 实际 8万×25/1000 = 2000 元。**差异不是平台"偷量"，而是你用了过程口径当结算口径**。若拿这 3000 去对账，就会凭空多出 1000 元的"无效争论"。

> ⚠️ 把"排障口径"和"结算口径"混用，团队里就会反复出现"明明展示很多为什么收入不对""报表说没问题为什么线上没广告"。

> 🧪 **自测**：算真实到账收入，该看 SDK 展示×预估 eCPM，还是平台 API 结算数据？

## 10. 读懂 eCPM + 收入波动归因：先分"平台预算"还是"用户质量"

穿山甲把 CPM 拆成（很好的教学公式 [[4]](https://www.csjplatform.com/growthcenter/6101274400195d0046c2731d)）：`CPM = 广告主出价 × 点击率 × 转化率 × 1000`。

**哪些你能动、哪些不能：**

- 相对可控：广告位置/时机、样式/尺寸、可点击元素、用户路径是否顺、预加载与展示成功率、分渠道/国家/用户分层策略。
- 相对不可控：广告主大盘预算、节假日整体出价波动、平台对用户价值与转化概率的判断模型。

**当填充率和 eCPM 同时下滑，先分两个大方向**（机制：两者的"指纹"不同）：

| 维度 | 平台预算波动 | 用户质量下降 |
|---|---|---|
| 范围 | 多产品/多广告位同时波动、节假日前后明显 | 同平台不同渠道差异大、换了新增来源后变化 |
| 伴随信号 | 同行业也在反馈 | CTR/CVR/填充一起变差 |
| 关键信号 | 某平台在特定国家下滑 | **连开屏 eCPM 也走弱** |
| 第一动作 | 扩平台互补、调 waterfall 兜底、找平台 BM | 回买量端查渠道/版位/机型/素材 |

> 💡 **开屏 eCPM 几乎不可操作，所以它是用户质量的好信号**——机制：开屏没有"位置/样式/可点击区"这些变现侧杠杆，它若走弱，基本排除了"广告位设计问题"，根因大概率在流量质量。

**CTR 不能靠"误点"赌**：误点短期抬 CTR，但后向转化跟不上，eCPM 未必真起，反伤体验与留存，平台还会据此判定流量质量下降。正确方向 [[4]](https://www.csjplatform.com/growthcenter/6101274400195d0046c2731d)：广告元素完整展示、适当增大尺寸、扩大合理可点击区（不是只留小按钮）、缩短点击后跳转路径。高质量 CTR 是"用户愿意点"，不是"用户不小心点"。

> 🧪 **自测**：某渠道用户连开屏 eCPM 都明显低于大盘，你先怀疑广告位设计还是流量质量？

## 11. 展示 GAP / 收益 GAP：什么时候正常、什么时候报警

TopOn 的 GAP 文档是很好的"口径课" [[6]](https://help.toponad.net/cn/docs/Z4zsF6)。

- **展示 GAP** = `(展示 − 展示API) / 展示API`：SDK 统计展示与平台 API 认定展示的差。
- **收益 GAP**：聚合侧预估/API 收益与平台实际收益的差。

**先别慌的情况**（机制：本就不该完全重合）：API 拉取有时延、不同时区天然偏差、最新数据不稳、预估 ≠ 真实。看到 GAP 先做三件事：① 确认比的是同一天同时区；② 确认 API 授权已开通；③ 确认过了平台/聚合更新时间。

**该重点排查代码/无效展示的情况**：展示 API 明显 < SDK 展示时，查——老版本没走聚合 SDK 请求、广告位 ID 复用、某源被判无效展示、Banner/原生被遮挡或可视面积不足、展示时长太短。

> ⚠️ 收益差很多，别一上来怪平台"偷量"。先排时区、API 授权、ID 复用、展示有效性、老版本分流这些最常见原因。

> 🧪 **自测**：展示 GAP 高达 30%，你的前三个排查动作是什么？（提示：时区、API 授权、更新时间，再谈代码。）

## 12. A/B 测试：小流量、强护栏、看全链路

A/B 的定义：用真实数据比较多种变现策略选最优，一般按用户属性分组、不大尺度破坏体验。

**值得测**：广告位位置、Waterfall 排序与底价、激励入口文案/奖励强度、插屏频率/间隔/时机、预加载时机与缓存条数、兜底源开关、新样式。

**必须至少看三层指标**（少看一层就会被带偏）：

```text
主指标：ARPDAU / 人均广告收入 / LTV
过程指标：渗透率、请求率、填充率、展示率、eCPM、CTR
护栏指标：D1/D7 留存、时长、启动次数、投诉、卸载、付费转化
```

**机制：为什么"eCPM 提升了"不能直接宣布胜利？** 三种常见假象——① 频率降了、低价值展示少了，eCPM 看起来高但总收入低；② 用户被打断更多，短期收入升但 D7 留存掉；③ 某国提价有效但整体样本结构变了，结论不稳。**广告实验必须看"价 × 量 × 留存"的乘积，而不是任一单点。**

> 🧪 **自测**：实验组 eCPM +15%、ARPDAU 持平、D7 留存 −3%，该上线吗？（提示：这是在用留存换短期单价，多半不该。）

## 13. 上线 SOP + 新人成长路径

**新广告位上线 SOP（设计—配置—验收—复盘）：**

```text
需求 → 研究市场/同类/商业模式 → 补齐基础信息与素材 → 对接主路径与商业化设计
→ 输出广告埋点方案 → 申请投放/广告参数 → 后台创建广告源与广告位
→ 测试包验收（样式/触发/回调/数据）→ 切正式 ID → 上线监控与复盘
```

埋点方案至少写清：广告位名称与 ID、所在页面与触发条件、样式、频次/间隔/上限、预加载时机、兜底逻辑、回调事件、是否分国家/渠道/版本。验收别只看"有没有出来"——AdMob/MAX 都提示新 App/新 ad unit 可能需要激活时间，要用测试模式/调试器/错误码/检查器验证 [[2]](https://support.google.com/admob/answer/9469204?hl=en)[[3]](https://support.applovin.com/en/max/getting-started)；覆盖显示层、功能层、数据层、策略层四层。

**新人三阶段（能力递进）：** 理解框架（会看报表、懂样式与链路）→ 会做诊断（独立回答"为什么这个位请求/Ready/eCPM 差"）→ 会做策略（能带一条产品线、串产品/投放/客户端/数据、提假设并验证）。成熟度路径：**记指标 → 看漏斗 → 找根因 → 提策略 → 做验证 → 形成 SOP。**

> 🧪 **自测**：验收时广告"显示正常"，但你还必须验哪三层才算过？（功能层、数据层、策略层。）

## 常见误区速扫

1. 只看 eCPM 不看展示量——高价没量收入照样差。
2. 只看填充率不看单价——全填低价流量浪费高价值展示。
3. 把广告位设计当"插几个点"——没有路径分析就容易埋深。
4. 预加载越早越好——错，太早缓存浪费、展示率下降、伤平台判断。
5. 广告源越多越好——看不清调不动的源只增噪音。
6. SDK 统计就是结算收入——错，SDK 看过程、API 看结算。
7. CTR 靠误点做高——短期有效、长期伤 CVR/留存/平台判断。
8. 看到 GAP 就怪平台——先排时区、API 授权、ID 复用、有效展示、老版本分流。
9. A/B 只看收入——不看留存与投诉就是在透支产品。
10. 新版本不分版本看漏斗——很多变现问题其实是新版本逻辑变了。
11. 把竞价当万能药——基础链路没稳，上复杂调度只会放大问题。
12. 变现与买量割裂——用户质量问题常先体现在 eCPM 和填充上。

```text
核心公式
广告收入 = 展示次数 × eCPM / 1000
ARPDAU  = 人均展示次数 × eCPM / 1000
人均展示次数 = 渗透率 × 人均请求PV × 填充率 × 展示率
CPM = 广告主出价 × CTR × CVR × 1000

判断主线（先量后价）
收入 = DAU × ARPDAU；ARPDAU 掉 → 先看人均展示(量) 还是 eCPM(价)
抬价是否划算：价的涨幅 × 量的跌幅，乘积 > 1 才赚

广告链路
初始化 → 获取策略 → 请求 → 填充 → 到达场景 → Ready → 触发展示 → 展示成功 → 点击/转化

三种调度（各自优先解决）
并行：有没有广告可卖（保填充/响应）
瀑布：能不能卖得更贵（保价格，维护重）
竞价/Hybrid：谁真愿出最高价（实时抬价 + 瀑布兜底）

四类常见问题
请求低：场景埋深 / 代码未触发 / 频控过严
填充低：底价高 / 源少 / 预算不足 / 用户质量差
Ready低：预加载太晚 / 缓存失效 / 请求时机不对
展示低：展示失败 / UI遮挡 / 无效展示 / 广告过期

数据口径
排障看 SDK/漏斗；对账看 API/平台后台；预估收益 ≠ 结算收益

收入波动归因
开屏 eCPM 也走弱 → 大概率用户质量；多产品同步波动+节假日 → 大概率平台预算
```

## 全文总结

IAA 变现的本质是把**用户会到达的广告机会**以尽量高的价格、尽量高的售卖成功率、尽量低的体验损伤卖出去；诊断主线永远是 `人均展示次数 × eCPM` 这棵收益树——**先判断是"量"还是"价"出了问题，再一路拆到叶子**（脊柱见第 1 章）。

- **量**这支 = 渗透率 × 人均请求PV × 填充率 × 展示率；**价**这支由出价、CTR/CVR、地区/渠道/用户质量、样式与位置决定。只看 eCPM 不看售卖率与展示率是头号坑（抬价是否划算，取决于"价涨幅 × 量跌幅"的乘积是否 > 1）。
- **样式与广告位**按用户场景选、按用户路径经营；激励的杠杆在奖励是否真有价值，不在按钮位置。
- **售卖与调度**：并行保填充、瀑布保价格、竞价/Hybrid 兼顾——基础链路没拉通别上复杂调度；很多"收入问题"其实是预加载/缓存/兜底的工程问题。
- **数据口径**（结算/SDK/预估）绝不混看；收入波动先分"平台预算 vs 用户质量"（开屏 eCPM 走弱是质量信号），再按漏斗"哪一格掉了"开动作单。
- **A/B 小流量、强护栏、看价×量×留存全链路**；新广告位走"设计—配置—验收—复盘"SOP。

一句话收束：**把收入当成一棵可运营的树**——任何波动先落到"量/价"两类根因，再沿漏斗和口径逐层定位，而不是笼统地说"今天 eCPM 掉了"。

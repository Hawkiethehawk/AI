# 混合变现应用的数据埋点与数据分析学习文档

> 这里把“混变应用”理解为：同时依赖广告变现 IAA 和内购/订阅 IAP 的移动应用。本文面向产品、运营、增长、数据分析和客户端研发，默认读者已经知道 DAU、留存、转化率、ARPU 等基础指标。
> 读完后，你应该能：设计一套不乱、不漏、不重复的埋点方案；区分广告、购买、订阅、留存数据的口径；用漏斗和收入拆解定位问题。

> 数据来源说明：本文主要是方法论梳理，不引用行业绝对基准。带数字的例子均为“示意”，不是行业标准。官方参考资料见文末。

---

## 0. 一句话理解

混合变现应用的数据系统，本质上不是“多埋几个事件”，而是把用户路径、广告路径、付费路径、订阅状态、收入归因统一到同一个用户生命周期里。

最核心的心智模型是：

```text
总收入 = 用户规模 x 用户活跃质量 x 广告变现效率 + 付费转化效率 x 续费/留存质量
```

拆开看：

```text
Revenue
├─ IAA 广告收入
│  ├─ DAU
│  ├─ 人均广告展示次数
│  ├─ 展示成功率
│  ├─ eCPM
│  └─ 广告位/地区/平台/渠道结构
└─ IAP/订阅收入
   ├─ Paywall 曝光人数
   ├─ 试用/购买转化率
   ├─ 续费率
   ├─ 退款/取消/宽限期/账单重试
   └─ 商品包、价格、权益结构
```

## 1. 主线：先建“用户生命周期 x 变现路径”

不要从事件名开始设计埋点。先画路径。

一个混合变现应用通常有五层路径：

```text
获客
  ↓
激活
  ↓
核心功能使用
  ↓
变现触点
  ├─ 广告展示
  └─ 付费/订阅
  ↓
留存与复购
```

埋点要覆盖每层的“到达、尝试、成功、失败、收入、状态变化”。

示例：

```text
用户打开 App
  → 完成首个核心任务
  → 看到广告场景
  → 广告请求
  → 广告填充
  → 广告展示
  → 产生展示级收入

用户打开 App
  → 触发付费墙
  → 查看套餐
  → 点击购买
  → 商店购买成功
  → 服务端校验成功
  → 进入订阅有效状态
```

这两个路径必须能按同一批用户、同一渠道、同一版本、同一地区进行对比。否则你只能看到“收入涨跌”，看不到“为什么涨跌”。

## 2. 第一个大坑：客户端事件不等于结算收入

混合变现最容易错的地方，是把客户端实时埋点当成最终收入口径。

广告侧尤其明显。Firebase 支持通过 `ad_impression` 记录广告收入事件，事件里可以包含广告平台、来源、币种和价值等信息 [[1]](https://firebase.google.com/docs/analytics/measure-ad-revenue)。AdMob 的展示级广告收入也用于更精细地计算用户 LTV [[2]](https://developers.google.com/admob/android/impression-level-ad-revenue)。但这些数据更适合做近实时分析、归因和用户级 LTV 估算，最终财务结算仍应以广告平台、聚合平台或商店后台的结算数据为准。

IAP/订阅同理。App Store Server API 用于从服务端请求和提供用户内购信息 [[3]](https://developer.apple.com/documentation/appstoreserverapi)，App Store Server Notifications 能通知订阅状态变化、退款等关键事件 [[4]](https://developer.apple.com/help/app-store-connect/configure-in-app-purchase-settings/enter-server-urls-for-app-store-server-notifications/)。Google Play 的实时开发者通知需要配置 Cloud Pub/Sub，并用于接收订阅和购买相关变化 [[5]](https://developer.android.com/google/play/billing/getting-ready)。

所以数据层至少要分三类口径：

| 口径 | 来源 | 主要用途 | 风险 |
|---|---|---|---|
| 客户端行为事件 | App SDK | 漏斗、路径、实时问题定位 | 丢包、重复、离线延迟 |
| 服务端/商店事件 | App Store、Google Play、支付服务端 | 订阅状态、退款、续费、权益判断 | 回调延迟、状态机复杂 |
| 结算/归因收入 | 广告平台、聚合平台、归因平台、财务后台 | ROI、ROAS、LTV、财务对账 | 与实时事件存在差异 |

做分析时先问一句：我现在看的数，是行为数、估算收入，还是结算收入？

## 3. 埋点设计原则

### 3.1 事件分层，而不是堆事件

建议分成六类事件：

| 层级 | 事件目标 | 例子 |
|---|---|---|
| 生命周期 | 用户从安装到留存 | `app_open`、`first_open`、`session_start` |
| 核心行为 | 用户是否获得产品价值 | `task_start`、`task_complete`、`feature_use` |
| 广告链路 | 广告从请求到收入 | `ad_scene_enter`、`ad_request`、`ad_filled`、`ad_impression` |
| 付费链路 | 付费墙到购买 | `paywall_show`、`package_click`、`purchase_start`、`purchase_success` |
| 订阅状态 | 续费、取消、退款、宽限期 | `subscription_renewed`、`subscription_canceled`、`refund` |
| 实验与配置 | A/B、价格、广告频控 | `experiment_exposed`、`remote_config_applied` |

Google Analytics / Firebase 本身提供推荐事件机制，官方建议优先使用推荐事件来衡量常见业务行为 [[6]](https://developers.google.com/analytics/devguides/collection/ga4/reference/events)。电商/购买类事件也有官方定义，例如 `purchase` 等电商测量事件 [[7]](https://developers.google.com/analytics/devguides/collection/ga4/ecommerce)。原则是：能用官方推荐事件就先用官方事件，业务独有行为再自定义。

### 3.2 每个事件必须回答四件事

一个合格事件要能回答：

```text
谁：user_id / device_id / anonymous_id / install_id
何时：event_time / client_time / server_time
在哪里：page / scene / placement / entry
发生了什么：event_name + params
```

混合变现还要额外回答：

```text
属于哪个变现模型：ad / iap / subscription / hybrid
属于哪个实验：experiment_id / variant_id
属于哪个版本：app_version / build_number / config_version
属于哪个渠道：media_source / campaign / adset / creative
属于哪个地区和平台：country / language / platform / os_version
```

### 3.3 广告埋点要记录“场景”，不能只记录展示

广告分析如果只有 `ad_impression`，只能知道“展示了多少”。要知道为什么展示少，必须记录前置链路：

```text
ad_scene_enter
  → ad_request
  → ad_load_success / ad_load_fail
  → ad_ready
  → ad_show_attempt
  → ad_impression
  → ad_click
  → ad_reward_granted
```

关键参数：

| 参数 | 含义 |
|---|---|
| `ad_placement_id` | 广告位 ID |
| `ad_format` | banner / interstitial / rewarded / native |
| `ad_network` | 实际展示广告网络 |
| `mediation_platform` | 聚合平台 |
| `scene` | 触发场景，例如任务完成页 |
| `is_first_ad_in_session` | 是否本次会话首个广告 |
| `load_latency_ms` | 加载耗时 |
| `error_code` | 加载或展示失败原因 |
| `value` | 展示级收入，若平台支持 |
| `currency` | 收入币种 |

注意：不要只看广告展示次数。展示次数下降可能是广告请求减少、填充下降、场景到达下降、展示失败、频控变严、或者用户任务完成率下降。

### 3.4 付费埋点要记录“意图”和“结果”

IAP/订阅链路至少要覆盖：

```text
paywall_trigger
  → paywall_show
  → package_view
  → package_click
  → purchase_start
  → purchase_success / purchase_fail
  → receipt_validate_success
  → entitlement_granted
```

关键参数：

| 参数 | 含义 |
|---|---|
| `paywall_id` | 付费墙版本 |
| `trigger_scene` | 触发来源 |
| `product_id` | 商品 ID |
| `offer_id` | 优惠/试用 ID |
| `price` | 展示价格 |
| `currency` | 币种 |
| `billing_period` | 周/月/年 |
| `trial_available` | 是否展示试用 |
| `failure_reason` | 失败原因 |
| `transaction_id` | 交易 ID，注意脱敏与权限 |
| `entitlement_id` | 发放权益 |

订阅类尤其不能只埋 `purchase_success`。取消、续费失败、宽限期、账单重试、退款、恢复购买，都决定真实 LTV。

### 3.5 实验埋点必须先于业务事件

如果要做 A/B 测试，必须先记录用户进入了哪个实验组：

```text
experiment_exposed
  - experiment_id
  - variant_id
  - assignment_time
  - assignment_unit: user / device / install
```

然后所有广告、付费、留存指标都要能按 `variant_id` 切开。否则测试上线后，只能看总体指标，很难判断变化来自实验还是流量结构。

## 4. 埋点注意事项清单

1. 事件名稳定，不要随版本随意改名。改名会导致历史趋势断裂。

2. 参数枚举要有字典。比如 `ad_format` 只能是固定值，不能一会儿写 `reward`，一会儿写 `rewarded_video`。

3. 收入事件必须带币种。多国家应用不能只存金额，不存 `currency`。

4. 客户端时间和服务端时间都要保留。跨时区、离线补发、归因回传都依赖时间口径。

5. 同一事件要有去重键。购买、广告收入、服务端回调尤其需要 `event_id` 或交易唯一 ID。

6. 不要把用户隐私数据直接放进埋点。广告标识符、设备标识符、邮箱、手机号等要按隐私合规要求处理。Apple 的 ATT 框架用于请求跟踪授权并返回授权状态 [[8]](https://developer.apple.com/documentation/apptrackingtransparency)，Google UMP SDK 用于管理用户隐私选择 [[9]](https://developers.google.com/admob/android/privacy)。

7. 客户端成功不等于服务端成功。`purchase_success` 之后还要看票据校验和权益发放。

8. 广告展示收入要允许延迟补齐。某些平台的展示级收入回调、聚合平台报表、归因平台数据可能时间粒度不同。

9. 不要只埋转化成功，也要埋失败原因。失败事件是定位问题的入口。

10. 每次版本上线都要做埋点验收。尤其检查广告场景、付费墙、订阅回调、实验分组是否正常。

## 5. 怎样做数据分析

### 5.1 先看总盘，再拆结构

混合变现日报建议按这个顺序看：

```text
收入总览
  → IAA / IAP 收入占比
  → DAU / 新增 / 留存
  → ARPDAU / ARPU / LTV
  → 广告链路
  → 付费链路
  → 订阅状态
  → 渠道、地区、平台、版本、实验分组
```

不要一上来就看 eCPM 或付费转化率。单点指标会误导。

示意：

```text
总收入下降
├─ DAU 下降？
├─ IAA 收入下降？
│  ├─ 展示人数下降？
│  ├─ 人均展示下降？
│  ├─ 填充/展示成功下降？
│  └─ eCPM 下降？
└─ IAP 收入下降？
   ├─ paywall 曝光下降？
   ├─ 点击购买下降？
   ├─ 支付成功率下降？
   ├─ 续费下降？
   └─ 退款/取消上升？
```

### 5.2 广告收入分析：用漏斗定位

广告收入可以拆成：

```text
广告收入 = 展示次数 x eCPM / 1000

展示次数 = DAU x 人均场景到达 x 请求率 x 填充率 x 展示成功率
```

分析路径：

1. 看 DAU 是否变化。
2. 看广告场景到达人数是否变化。
3. 看请求次数是否变化。
4. 看加载成功率、填充率、展示成功率。
5. 看 eCPM 是否变化。
6. 按广告位、广告格式、国家、平台、版本拆分。

常见判断：

| 现象 | 可能原因 |
|---|---|
| DAU 稳定，展示下降 | 场景入口变少、频控变严、广告加载失败 |
| 展示稳定，eCPM 下降 | 广告网络需求变化、流量结构变化、低价值广告位占比上升 |
| eCPM 上升，收入下降 | 展示量损失大于单价提升 |
| 填充高但展示低 | 预加载过早、缓存过期、用户未到达展示场景 |
| 激励视频点击低 | 奖励价值不足或触发场景不对 |

### 5.3 付费分析：从付费墙漏斗到订阅状态机

付费漏斗：

```text
核心功能触发
  → 付费墙曝光
  → 套餐点击
  → 发起购买
  → 商店支付成功
  → 服务端校验成功
  → 权益发放成功
```

核心指标：

| 指标 | 公式 |
|---|---|
| Paywall 曝光率 | paywall_show_users / active_users |
| 付费墙点击率 | package_click_users / paywall_show_users |
| 购买发起率 | purchase_start_users / paywall_show_users |
| 支付成功率 | purchase_success_users / purchase_start_users |
| 权益发放成功率 | entitlement_granted / purchase_success |
| 退款率 | refund_users / purchase_users |
| 续费率 | renewed_subscriptions / renewable_subscriptions |

订阅分析不能只看首购。要把用户放进状态机：

```text
未订阅
  → 试用中
  → 订阅有效
  → 续费成功
  → 续费失败
  → 宽限期
  → 暂停/过期
  → 退款/撤销
  → 恢复订阅
```

分析时要区分主动取消和被动流失。主动取消通常是价值感、价格、预期管理问题；被动流失通常是支付失败、账单重试、卡问题或平台机制问题。

### 5.4 混合变现分析：看“广告和付费是否互相伤害”

混合变现不是 IAA + IAP 简单相加。广告会影响付费意愿，付费也会减少广告展示。

必须看这些交叉指标：

| 问题 | 分析方式 |
|---|---|
| 广告是否伤害付费？ | 对比高广告曝光用户和低广告曝光用户的付费墙转化、次日留存 |
| 付费是否减少广告收入？ | 订阅用户是否去广告；计算订阅收入是否覆盖广告损失 |
| 激励广告是否替代付费？ | 看激励视频用户后续购买率和功能使用深度 |
| 付费墙是否过早？ | 按新用户第几次核心任务触发付费墙切分 |
| 广告频控是否合理？ | 看频次分桶下的 ARPDAU、留存、卸载、付费率 |

示意分析表：

| 用户分组 | 广告收入 | 付费收入 | 留存 | 结论 |
|---|---:|---:|---:|---|
| 低广告曝光 | 低 | 中 | 高 | 适合观察付费潜力 |
| 中广告曝光 | 中 | 中 | 中 | 可能是均衡区 |
| 高广告曝光 | 高 | 低 | 低 | 可能透支体验 |

表中数字方向仅为示意，真实结论必须来自自己的分桶数据。

## 6. 日常分析 SOP

### 每日看板

```text
1. 总收入、IAA 收入、IAP 收入
2. DAU、新增、D1/D7 留存
3. ARPDAU、广告 ARPDAU、付费 ARPDAU
4. 广告展示人数、人均展示、eCPM、展示成功率
5. Paywall 曝光、购买发起、支付成功、退款
6. Top 国家、Top 渠道、Top 版本
7. 异常波动：按版本、国家、广告位、商品包拆
```

### 每周复盘

```text
1. 哪个收入因子贡献最大？
2. 哪个用户分群 LTV 最高？
3. 哪个广告位伤害留存或付费？
4. 哪个 paywall 版本转化最好？
5. 哪个渠道 ROI/ROAS 最稳定？
6. 新版本是否引入埋点或收入口径异常？
```

AppsFlyer 的收入归因产品用于把收入数据用于 ROI/ROAS 分析，并支持广告收入相关数据在看板和原始数据报告中使用 [[10]](https://support.appsflyer.com/hc/en-us/articles/360001546009-ROI360-revenue-attribution-overview)。如果团队做投放，最好把广告收入、IAP 收入、渠道归因和成本放进同一套 LTV/ROI 数据模型里。

### A/B 测试分析

每个实验至少定义：

```text
假设：为什么改
主指标：希望提升什么
护栏指标：不能伤害什么
分层维度：平台、国家、渠道、新老用户
停止条件：什么时候停
上线条件：什么结果才全量
```

例子：

```text
实验：任务完成页插屏频控从较高频改为较低频
主指标：总 ARPDAU
护栏指标：D1 留存、D7 留存、付费转化率、崩溃率
分层：新用户 / 老用户，Android / iOS，主要国家
判断：如果广告收入下降，但留存和付费提升后总 LTV 更高，可以考虑上线
```

## 7. 常见错误

1. 只埋成功事件，不埋失败事件。

2. 只看收入，不看 DAU、留存、用户结构。

3. 把广告 SDK 估算收入当结算收入。

4. 把客户端购买成功当订阅有效。

5. 没有记录 paywall 版本，导致无法分析付费墙实验。

6. 没有记录广告位场景，只知道广告展示，不知道为什么展示。

7. 没有去重键，购买和回调重复计算。

8. 只看整体平均，不按国家、渠道、平台、版本拆分。

9. 事件名和参数没有字典，导致同一含义多种写法。

10. 忽视隐私同意状态，把不可用用户混进同一口径。

## 附：一页速查表

```text
混合变现核心公式：
总收入 = IAA 收入 + IAP/订阅收入

IAA：
广告收入 = 展示次数 x eCPM / 1000
展示次数 = DAU x 场景到达率 x 请求率 x 填充率 x 展示成功率 x 人均频次

IAP：
付费收入 = Paywall 曝光人数 x 点击率 x 购买发起率 x 支付成功率 x 客单价
订阅收入 = 首购收入 + 续费收入 - 退款/撤销

必须埋点：
生命周期：app_open / session_start / first_open
核心行为：task_start / task_complete / feature_use
广告：ad_scene_enter / ad_request / ad_load_success / ad_show_attempt / ad_impression / ad_click
付费：paywall_show / package_click / purchase_start / purchase_success / receipt_validate_success / entitlement_granted
订阅：subscription_renewed / subscription_canceled / billing_retry / grace_period / refund
实验：experiment_exposed / remote_config_applied

必须参数：
user_id、anonymous_id、event_time、app_version、platform、country、media_source、campaign、experiment_id、variant_id
广告参数：ad_placement_id、ad_format、ad_network、scene、value、currency、error_code
付费参数：paywall_id、product_id、offer_id、price、currency、billing_period、failure_reason、transaction_id

分析顺序：
先总收入 → 分 IAA/IAP → 拆 DAU/ARPU → 拆漏斗 → 拆国家/渠道/平台/版本/实验 → 找根因
```

# Version Manager

统一处理版本决策和 Git 发布。先识别仓库与项目，再执行对应阶段；不得把检查、改版本、提交和推送合并成一个隐式操作。

## 固定边界

- `E:\LLM-Sandbox\Codex`、`F:\AMTools`、`F:\Monety`、`F:\ADGuide` 是独立仓库。始终用 `git rev-parse --show-toplevel` 确认根目录。
- 只处理用户指定的仓库和文件。不得跨仓库暂存、提交、打标签或推送。
- `archived/` 只作历史材料，不作为运行、发布或版本判断来源。
- 保留用户已有的未提交改动。暂存时列出明确路径，不使用覆盖整个仓库的隐式 `git add -A`。
- Git 远端写入必须由用户在当前对话明确要求。不得自动 pull、push、创建标签或部署。
- 版本规则以本 Skill 和 [references/project-profiles.md](references/project-profiles.md) 为唯一来源；项目 `AGENTS.md` 只处理非版本约束。
- 只有两类对象可以拥有版本：包含有效 `SKILL.md` 且路径已在项目配置中声明的 Skill，以及明确配置为复合项目的仓库根。AI、Monety 等承载仓库本身、普通应用、脚本、文档目录和未配置仓库均不设置或推断版本。
- 非版本对象仍可使用本 Skill 完成检查、提交和远端发布；不得修改版本文件或创建版本标签，但每次推送仍必须更新仓库级 CHANGELOG 并创建维护标签。
- 任何推送都必须同时包含与待推送内容一致的 CHANGELOG 更新，并至少推送一个新建、不可变且指向本次推送 HEAD 的标签。缺少任一项时禁止推送。

## 工作流

### 1. 检查

只读检查可直接执行：

1. 解析仓库根、当前分支、远端、工作区和暂存区。
2. 按 [references/project-profiles.json](references/project-profiles.json) 读取目标项目的对象类型、版本源和标签规则；组件版本不得自动当作仓库版本。
3. 用 `scripts/version_inspect.py --repo <repo> [--project <path>]` 生成统一摘要。脚本不访问网络、不写文件；普通目录和未配置仓库不得回退到通用版本扫描。
4. 查看仓库及目标子目录的 `AGENTS.md`，但只应用安全、验证、部署和项目边界；忽略其中残留的版本更新规则，并报告迁移遗漏。

### 2. 分类

按待发布差异分类：

- Patch：缺陷修复、稳定性或兼容性修复、测试补强、文档更新及不改变功能或 UI 的维护性调整。Patch 是变更分类，不是第三段版本号，也不触发版本发布。
- 功能更新：新增或改变向后兼容的功能、UI、依赖能力或用户使用方式。
- 破坏性更新：产生破坏兼容性的外部接口、数据契约或使用方式变更。
- 混合变更：按其中影响最大的类型处理；提交前明确列出纳入范围。

默认版本决策：

- 先确认目标是已配置的 Skill 或复合项目。其他对象直接判定为“无版本”，不进入版本号决策。
- 用户指定版本号时使用指定值。
- 版本固定使用 `主版本.次版本` 两级格式，例如 `1.2`；不得创建或继续使用第三段版本号。除非用户明确要求迁移整个版本体系，否则不得修改版本层级或标签格式。
- Patch 不修改版本源，也不创建或移动版本标签；推送 Patch 时必须更新仓库级 CHANGELOG，并创建 `patch-YYYYMMDD-HHMMSS` 维护标签。维护标签在提交前确定并写入 CHANGELOG，它不是版本号，不得写成第三段版本。
- 只有功能、UI 或其他用户能力发生新增或改变时才发布新版本：向后兼容的更新递增次版本；破坏性更新递增主版本并将次版本归零。
- 不得因为用户使用“Patch”一词而推断需要第三段版本。除非用户明确要求迁移整个版本体系，否则始终保持两级版本和现有标签格式。
- 同一批变更包含兼容与破坏兼容两类时按破坏兼容处理。无法判断兼容性时不得自动选择版本，必须说明不确定点并请求用户确认。
- 版本建议只是发布确认的一部分；写入前必须由用户确认。用户可以指定其他版本覆盖建议。
- 用户明确要求不修正版本号时保持当前版本；仍需按发布授权执行后续步骤。
- 本地修改、验证、普通提交或拉取不自动递增版本号。版本号只在准备远端发布时处理；CHANGELOG 和标签硬约束只在准备推送时触发。

### 3. 发布确认

任何版本文件、CHANGELOG 或标签写入前，先报告并等待明确确认：

- 仓库、项目、分支和远端；
- 待发布文件与变更分类；
- 当前版本和拟发布版本；
- 功能变化、影响范围与验证结果；
- 将更新的版本文件、CHANGELOG、README、提交和标签；
- 推送及项目要求的部署或外部文档同步。

用户只授权修改代码，不等于授权版本发布。用户只说“提交”，不等于授权推送。用户只说“推送”，若尚未确认拟发布版本，仍需先完成版本确认。

### 4. 更新版本材料

- 使用项目配置声明的版本源。Node 复合项目可使用独立 `VERSION` 文件，并由 CLI 读取该文件。
- 普通版本对象的 `CHANGELOG.md` 记录版本号、发布日期、实际变更和本次真实执行的验证结果。不得把未运行的测试写成已通过。
- 每次推送都更新项目配置声明的仓库级 CHANGELOG。功能或破坏性版本发布写版本条目；Patch 写维护条目，记录日期、实际变更、实际验证和维护标签，不伪造新版本。
- Skill 遵守 `skill-creator` 的目录约束，不在 Skill 目录创建 `CHANGELOG.md`；Skill 推送使用承载仓库根 CHANGELOG。功能更新同时使用 `SKILL.md` 版本字段和同版本标签；Patch 仅使用维护标签。
- 如果目标仓库尚无配置的 CHANGELOG，首次推送前在仓库根创建 `CHANGELOG.md`；不得因对象无版本而跳过变更记录。
- 只同步项目资料中明确展示的当前版本；具体文件见项目配置。
- 更新后重新读取全部版本来源，确认版本一致且差异只包含预期文件。

### 5. 提交与标签

1. 运行项目要求的验证。
2. 更新仓库级 CHANGELOG，并确认其内容覆盖本次完整待推送范围和真实验证结果。
3. 用明确路径暂存并检查 `git diff --cached --stat` 和 `git diff --cached`。
4. 创建提交。不得顺带纳入用户的其他改动。
5. 按变更分类创建标签：功能或破坏性发布使用项目版本标签；Patch 使用提交前已写入 CHANGELOG 的 `patch-YYYYMMDD-HHMMSS` 维护标签。一次推送只要已有符合本次分类且指向 HEAD 的新标签即可，不重复创建两类标签。
6. 标签必须新建并指向本次推送 HEAD；本地或远端存在同名冲突时停止处理。禁止移动、覆盖或复用旧标签。

### 6. 远端发布

- 推送前重新确认工作区、分支、远端、领先/落后关系和标签指向。需要网络刷新时，先取得 pull/fetch 授权。
- Gitee 认证、AI 仓库适配和特殊发布入口见 [references/gitee.md](references/gitee.md)。
- 普通发布先同步目标分支，再原子推送明确分支和本次新标签；远端不支持原子推送时依次推送并逐项回读。禁止无租约强推。
- 推送前校验待推送提交范围包含本次 CHANGELOG 更新，且新标签指向 HEAD。任一条件不满足时禁止推送。
- 推送后读取远端引用核验提交和标签。涉及部署或外部文档同步时，按项目配置执行并回读验证。
- 未推送、未部署或未同步的动作必须明确列为未执行。

## 验收

- 仓库、项目、分支和远端正确，未跨仓库操作。
- 变更分类、当前版本和拟发布版本有证据支持。
- 所有版本来源一致；功能或 UI 版本发布都有对应版本记录和版本标签；Patch 没有伪造新版本，但有维护记录和维护标签。
- 每次推送的 CHANGELOG 只记录实际变更和真实验证结果，且本次新标签指向远端分支 HEAD。
- 暂存区不含无关文件，标签指向发布提交。
- 远端写入、部署和外部同步均有明确授权及回读结果。
- 最终反馈区分已验证、未执行和待确认事项。

# 指标拆解与诊断路径

## 收入拆解

先使用恒等关系定位变化来自规模还是价格：

```text
revenue = impressions × ecpm / 1000
```

比较当前周期与基线周期，并分别计算展示量和 eCPM 的变化。两者同时变化时，继续按国家、广告位、广告样式、广告源、版本和流量分组做贡献拆解。

不要只看相对变化。报告当前值、基线值、绝对变化、相对变化和对总收入差额的贡献。

## 请求到展示漏斗

在字段口径允许时使用：

```text
requests -> responses -> impressions -> clicks
```

依次检查：

1. 请求量是否随活跃用户、场景触发或版本变化。
2. 返回或填充是否变化，以及变化集中在哪个国家、广告位或广告源。
3. 返回到展示的转化是否变化，检查超时、缓存、预加载、用户离开和展示条件。
4. 点击变化是否来自展示规模、素材或误触，不以 CTR 单独判断收入质量。

## eCPM 变化

将 eCPM 变化作为结果，优先排查流量结构：国家、平台、广告样式、用户价值、广告位和广告源占比。结构变化后再检查同一细分单元的 eCPM 是否变化。

候选原因包括竞价环境、底价、瀑布配置、广告源预算、隐私授权和流量质量。除非有配置记录、广告源反馈或实验数据，否则只标为 `[推断]`。

## 维度贡献

对每个维度计算：

```text
group_revenue_delta = current_group_revenue - previous_group_revenue
```

按绝对贡献排序。先解释少数主导变化，再处理长尾。维度之间可能重叠，国家贡献和广告位贡献不能相加为新的总变化。

对同一维度使用对称恒等拆分，将收入差额描述为展示量/结构效应与组内 eCPM 效应。该拆分用于缩小排查范围，不代表展示或 eCPM 变化的因果来源。每个维度的分组收入差额之和必须与总收入差额对账。

## 同期事件

把以下事件与时间线对齐：

- App 版本发布、SDK 或 Adapter 更新。
- 广告位触发、频控、预加载和展示逻辑修改。
- TopOn 流量分组、瀑布、竞价、底价或广告源启停。
- 用户获取渠道、国家结构或投放规模变化。
- CMP、ATT、GDPR 或其他合规流程变化。
- 节假日、广告平台事故、报表延迟和币种换算变化。

时间重合只能增加假设优先级，不能证明因果。

## 数据不足时的输出

列出当前能确认的变化，然后给最小补数清单。例如：缺少 `responses` 时可以确认展示下降，但不能区分填充下降和展示转化下降；缺少版本维度时不能验证发布影响。
